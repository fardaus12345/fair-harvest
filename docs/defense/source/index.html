1প্রজেক্ট পরিচিতি (Project Overview)[[C1]]

1.1 এক লাইনে Fair Harvest কী?

Fair Harvest একটি full-stack digital agricultural marketplace, যেখানে সরকারি Farmer Card দিয়ে verified কৃষকরা তাদের কৃষিপণ্য সরাসরি ক্রেতাদের কাছে বিক্রি করতে পারে, এবং প্রতিটি পণ্যের মাটি-থেকে-প্লেট (soil-to-plate) যাত্রা ক্রেতা নিজের চোখে দেখতে পারে।

Full-stack মানে হলো — frontend (যা ব্যবহারকারী চোখে দেখে) এবং backend (business logic, authentication, database, API) দুটোই একই application-এর ভিতরে আছে। এখানে আলাদা কোনো backend server নেই; Next.js একই সাথে UI render করে এবং app/api/v1/** ফোল্ডারে REST API চালায়।

1.2 কেন এই প্রজেক্ট বানানো হলো?

বাংলাদেশে একজন কৃষক ফসল ফলানোর পর সাধারণত সরাসরি ক্রেতার কাছে পৌঁছাতে পারেন না। মাঝখানে কয়েক ধাপ মধ্যস্বত্বভোগী থাকে। ফলে দুটো সমস্যা একসাথে হয় —

  • কৃষক ন্যায্য দাম পান না, কারণ তিনি দাম নির্ধারণ করতে পারেন না।
  • ক্রেতা জানেন না পণ্যটি আসলে কে ফলিয়েছে, কোথায় ফলিয়েছে, কবে তোলা হয়েছে।

Fair Harvest এই দুই পক্ষকে সরাসরি একটি প্ল্যাটফর্মে আনে, এবং মাঝখানে যে বিশ্বাসের অভাব তৈরি হতো সেটি পূরণ করার জন্য তিনটি আলাদা ব্যবস্থা রাখে: farmer verification, reputation score এবং traceability।

1.3 একটি সাধারণ e-commerce সাইট থেকে এটি আলাদা কেন?

সাধারণ e-commerceFair Harvest

1.4 কে কে ব্যবহার করে?

তিন ধরনের ব্যবহারকারী আছে, এবং database-এ এদের Role enum দিয়ে আলাদা করা হয়: CONSUMER, FARMER, ADMIN।

  • CONSUMER (ক্রেতা) — marketplace ঘুরে পণ্য দেখে, cart-এ রাখে, checkout করে, order track করে, delivered পণ্যের review দেয়।
  • FARMER (কৃষক) — Farmer Card verify করে, পণ্য যোগ/সম্পাদনা করে, ছবি upload করে, trace event লেখে, নিজের order ও earnings দেখে।
  • ADMIN (প্রশাসক) — verification queue দেখে approve/reject করে, account suspend করে, সব পণ্য ও order নিয়ন্ত্রণ করে, review moderate করে, audit log দেখে।

1.5 Admin-এর ভূমিকা কী?

Admin এই সিস্টেমে বিক্রি করে না, কেনেও না। Admin হলো নিরপেক্ষ তত্ত্বাবধায়ক। যে কৃষকের Farmer Card স্বয়ংক্রিয়ভাবে মেলেনি, তার আবেদন admin হাতে দেখে সিদ্ধান্ত দেন। কোনো অ্যাকাউন্ট খারাপ আচরণ করলে admin সেটি suspend করতে পারেন। এবং admin-এর প্রতিটি গুরুত্বপূর্ণ কাজ AuditLog টেবিলে লিখে রাখা হয় — যাতে পরে কে কী করেছে তা প্রমাণ করা যায়।

1.6 English technical summary

Fair Harvest is a single-deployment Next.js 15 App Router application that serves both the user interface and a versioned REST API under /api/v1. Persistence is handled by Prisma ORM against PostgreSQL (Neon in production). Authentication uses stateless HS256 JWTs held in localStorage; authorization is enforced server-side on every route through requireUser, requireRole and requireOwnerOrRole. The platform's differentiators — Government Farmer Card verification, a multi-signal farmer reputation score, purchase-gated reviews, and a farmer-authored soil-to-plate trace log — are all implemented as real database-backed features rather than static content.

এই হোমপেজটি একটি React Server Component; এটি server-এ render হওয়ার সময় SDK দিয়ে নিজের API-কে ডাকার চেষ্টা করে। যে module-গুলোর জন্য login বা seeded data দরকার, সেগুলোর জন্য preview/demo মান দেখায় এবং পৃষ্ঠার উপরে হলুদ ব্যানারে সেটা স্পষ্ট করে লিখে দেয় — এটি ইচ্ছাকৃত সততা, লুকানো নয়।

5সিস্টেম আর্কিটেকচার[[C5]]

5.1 এক কথায় আর্কিটেকচারটি কেমন?

Fair Harvest একটি monolithic full-stack Next.js application। অর্থাৎ frontend ও backend আলাদা দুটি প্রজেক্ট নয় — একটিই deployment, যেখানে একই server একদিকে HTML/React পাঠায়, অন্যদিকে /api/v1/**-এ REST API উত্তর দেয়।

5.2 স্তরগুলো কী কী?

স্তর (Layer)কাজপ্রধান ফাইল
Clientব্যবহারকারী যা দেখেন ও ক্লিক করেন। JWT token এখানে localStorage-এ থাকে। app/**/page.js, components/**
Routing / MiddlewareAPI-এর জন্য CORS নিয়ন্ত্রণ। default অবস্থায় শুধু same-origin অনুমোদিত, কোনো wildcard নেই। middleware.js
Route Handlers (API)প্রতিটি REST endpoint। HTTP method অনুযায়ী GET/POST/PATCH/DELETE function export করা হয়। app/api/v1/**/route.js
Auth layerটোকেন পড়া, ব্যবহারকারী শনাক্ত করা, রোল ও মালিকানা যাচাই। lib/server/auth.js
Business logicReputation গণনা, review eligibility, earnings সারাংশ, API response-এর আকার নির্ধারণ। lib/server/reputation.js, reviews.js, earnings.js, serializers.js
Cross-cuttingসব route-এ লাগে এমন জিনিস: rate limit, audit log, Zod validation, identifier masking, একক error format। rateLimit.js, audit.js, respond.js, mask.js
DataPrisma Client দিয়ে PostgreSQL-এ query; ছবি Vercel Blob-এ। lib/server/db.js, prisma/schema.prisma, lib/server/storage/

5.3 দুটি গুরুত্বপূর্ণ ডিজাইন সিদ্ধান্ত

(ক) Provider Abstraction — একই নকশা দুই জায়গায়

দুটি জায়গায় একই প্যাটার্ন ব্যবহার করা হয়েছে: একটি index.js ঠিক করে দেয় কোন provider ব্যবহার হবে, আর route handler কখনো জানেই না ভিতরে কোনটা চলছে।

lib/server/verification/index.js      lib/server/storage/index.js
  ├─ demoRegistryProvider.js            ├─ localDiskProvider.js   (dev)
  └─ officialGovApiProvider.js          └─ objectStorageProvider.js (Vercel Blob)
     ↑ VERIFICATION_PROVIDER               ↑ STORAGE_PROVIDER

লাভ কী? ভবিষ্যতে সত্যিকারের সরকারি API এলে শুধু একটি ফাইল বদলাতে হবে — route, database schema বা frontend-এর একটি লাইনও বদলাবে না। একই ভাবে local disk থেকে Vercel Blob-এ যেতে শুধু একটি environment variable বদলাতে হয়েছে।

(খ) Pure Function — যাতে টেস্ট করা যায়

যেসব logic-এ database লাগে না, সেগুলো আলাদা pure ফাইলে রাখা হয়েছে — reputation.js, reviewEligibility.js, earnings.js, imageValidation.js, mask.js, rateLimit.js। এতে node --test দিয়ে database বা Next.js runtime ছাড়াই ২৬টি unit test চালানো যায় (অধ্যায় 38)।

ভাইভা টিপ

যদি জিজ্ঞেস করে “আপনার architecture কি microservice?” — উত্তর: “না, এটি ইচ্ছাকৃতভাবে monolith। একজন ডেভেলপারের university project-এ microservice মানে অপ্রয়োজনীয় জটিলতা। তবে কোডের ভিতরে স্তর (layer) আলাদা রাখা হয়েছে, আর provider abstraction দিয়ে বাইরের নির্ভরতাগুলো পাল্টানোর পথ খোলা রাখা হয়েছে।”

components/RoleGuard.js একটি client component যা /account, /farmer/** ও /admin/** layout-এ মোড়ানো আছে। এটি দেখে ব্যবহারকারী login করা আছে কি না এবং রোল ঠিক আছে কি না; না হলে সঠিক জায়গায় পাঠিয়ে দেয়।

খুব গুরুত্বপূর্ণ (ভাইভায় প্রায়ই জিজ্ঞেস করা হয়)

RoleGuard নিরাপত্তা নয় — এটি শুধু ব্যবহারকারীর সুবিধা। কেউ browser-এর JavaScript বন্ধ করে বা সরাসরি API-তে request পাঠিয়ে এটি এড়াতে পারে। আসল নিরাপত্তা আছে server-এ: প্রতিটি protected route requireUser / requireRole / requireOwnerOrRole দিয়ে নিজেই যাচাই করে। কোডের কমেন্টেও এই কথাটি স্পষ্ট লেখা আছে।

8.1 শব্দ দুটি আগে পরিষ্কার করে নিই

English termসহজ বাংলা অর্থFair Harvest-এ কোথায়
Authentication“তুমি কি সত্যিই সেই লোক?” — পরিচয় প্রমাণ করা POST /auth/login → পাসওয়ার্ড মিলিয়ে JWT দেওয়া

8.2 JWT কী? (সহজ ব্যাখ্যা)

JWT (JSON Web Token) — একে ভাবুন একটি সিল করা পরিচয়পত্র। ভিতরে লেখা থাকে আপনি কে (sub = user id), আপনার রোল কী, ইমেইল কী, আর কতক্ষণ পর্যন্ত বৈধ (exp)। এর গায়ে server তার গোপন চাবি (JWT_SECRET) দিয়ে একটি signature বসায়। কেউ ভিতরের লেখা এক অক্ষর বদলালে signature আর মেলে না, তাই server সঙ্গে সঙ্গে বুঝে ফেলে।

// lib/server/auth.js
export function signToken(user) {
  return jwt.sign({ sub: user.id, role: user.role, email: user.email },
                  JWT_SECRET, { expiresIn: JWT_EXPIRES_IN });   // default "2h"
}

Stateless মানে — server-এ কোনো session টেবিল রাখতে হয় না। token নিজেই সব তথ্য বহন করে। Vercel-এর মতো serverless পরিবেশে এটিই সবচেয়ে উপযুক্ত, কারণ প্রতিটি request আলাদা function instance-এ চলতে পারে।

8.3 একজন কৃষক login করলে ভিতরে ঠিক কী কী ঘটে?

  1. কৃষক /auth/farmer পেজে email ও password লেখেন।
  2. AuthForm.js → lib/api.js-এর login() → POST /api/v1/auth/login।
  3. Route প্রথমেই enforceRateLimit(request, "auth-login", { max: 10, windowMs: 60000 }) চালায় — এক মিনিটে একই IP থেকে ১০ বারের বেশি চেষ্টা হলে 429।
  4. Zod loginSchema দিয়ে email ও password যাচাই; ভুল হলে 422।
  5. prisma.user.findUnique({ where: { email }, include: { farmerProfile: true } })।
  6. ব্যবহারকারী না থাকলে, বা status === "SUSPENDED" হলে — 401 "Invalid email or password"। লক্ষণীয় বার্তাটি ইচ্ছাকৃতভাবে একই রাখা হয়েছে, যাতে আক্রমণকারী বুঝতে না পারে ইমেইলটি আদৌ আছে কি না (user enumeration প্রতিরোধ)।
  7. bcrypt.compare(password, user.passwordHash) — পাসওয়ার্ড মেলানো হয় hash-এর সাথে, কখনো plain text-এর সাথে নয়।
  8. মিললে signToken(user) — HS256 JWT তৈরি।
  9. Response: { success: true, data: { access_token, token, user }, message: "Logged in" }।
  10. Browser-এ saveSession() টোকেন ও user object localStorage-এ রাখে এবং একটি custom event ছাড়ে, যাতে Navbar সাথে সাথে নাম দেখায়।
  11. এরপর প্রতিটি request-এ lib/api.js নিজে থেকেই Authorization: Bearer <token> header যোগ করে দেয়।

...(role === "farmer" ? { farmerProfile: { create: {} } } : {})
// farmer হলে একই সাথে একটি খালি FarmerProfile তৈরি হয় → verificationStatus = PENDING

একই ইমেইল আগে থেকে থাকলে 409 "An account with this email already exists"।

8.5 Logout ও টোকেনের মেয়াদ

  • Logout — clearSession() শুধু localStorage থেকে token ও user মুছে দেয়। JWT stateless, তাই server-এ “বাতিল করা” বলে কিছু নেই। সীমাবদ্ধতা logout-এর পরেও token তার মেয়াদ (২ ঘণ্টা) শেষ না হওয়া পর্যন্ত প্রযুক্তিগতভাবে বৈধ থাকে — কেউ যদি আগেই সেটি কপি করে নিত।
  • মেয়াদ শেষ — jwt.verify ব্যর্থ হয়, decodeToken null দেয়, requireUser 401 ছোড়ে, আর lib/api.js ৪০১ দেখে ব্যবহারকারীকে /auth-এ পাঠিয়ে দেয়।

8.6 Production-এ একটি নিরাপত্তা-তালা

9Authorization — কে কী করতে পারবে[[C9]]

9.1 তিনটি helper, তিন রকম প্রশ্ন

Helperকী প্রশ্ন করেব্যর্থ হলে
requireUser(request)“তুমি কি আদৌ login করা?” 401 Authentication required
requireRole(request, ["ADMIN"])“তোমার রোল কি অনুমোদিত তালিকায়?” 403 You do not have permission…
requireOwnerOrRole(request, ownerId, ["ADMIN"]) “এটা কি তোমারই জিনিস, নাকি তুমি admin?” 403
export function requireOwnerOrRole(request, ownerId, roles) {
  const session = requireUser(request);
  if (session.userId === ownerId || roles.includes(session.role)) return session;
  throw new ApiError("You do not have permission to perform this action", 403);
}

9.2 IDOR ঠেকানো — বাস্তব উদাহরণ

IDOR (Insecure Direct Object Reference) মানে — URL-এ অন্যের id বসিয়ে দিলে তার ডেটা দেখা যাওয়া। Fair Harvest-এ এটি নিয়মিতভাবে আটকানো হয়েছে।

আক্রমণের চেষ্টাকী ঘটে
GET /api/v1/cart/<অন্যের userId> requireOwnerOrRole(request, userId, ["ADMIN"]) → 403
GET /api/v1/orders/<অন্যের userId>একইভাবে 403
PATCH /api/v1/products/<অন্য কৃষকের পণ্য> assertOwnerOrAdmin() পণ্যটির farmer.userId মিলিয়ে দেখে → 403
GET /api/v1/wishlist — অন্যের wishlist চাওয়া এখানে URL-এ কোনো userId-ই নেই; route সবসময় session.userId ব্যবহার করে। অর্থাৎ ভুল id পাঠানোর সুযোগই নেই।
GET /api/v1/farmer/orders farmer profile session থেকে বের করা হয়, client থেকে নয়। তাই এক কৃষক অন্য কৃষকের order item দেখতে পারেন না।
PATCH /api/v1/orders/<id>/status ADMIN না হলে দেখা হয় — এই order-এর কোনো item কি এই কৃষকের? না হলে 403
GET /api/v1/orders/detail/<id> ADMIN নয় এবং session.userId !== order.userId → 403

একটি সুন্দর উত্তর তৈরি রাখুন

  2. Dashboard-এ সতর্কবার্তা — /farmer/dashboard-এ “Verification required — Product listing is locked until your Government Farmer Card is verified” লেখা একটি প্যানেল দেখায়, এবং “Add product” ফর্মটি একেবারেই render হয় না।
  3. ফর্ম পূরণ — /farmer/verify-তে তিনটি ঘর: Full name (as on card), Farmer Card number, NID number।
  4. API কল — POST /api/v1/farmers/{farmerId}/verify। প্রথমে rate limit (৮/মিনিট), তারপর requireOwnerOrRole(request, profile.userId, ["ADMIN"]) — অর্থাৎ একজন কৃষক অন্যজনের হয়ে আবেদন করতে পারেন না। তারপর Zod validation।
  5. Provider যাচাই — verifyFarmerCard() ডাকা হয় (বিস্তারিত অধ্যায় 11)।
  6. ডাটাবেস আপডেট — ফলাফল যাই হোক, জমা দেওয়া card ও NID সংরক্ষিত হয়: 
    verificationStatus: result.matched ? "VERIFIED" : "PENDING",
verificationMethod: result.matched
    ? (result.provider === "official" ? "OFFICIAL_API" : "DEMO_REGISTRY")
    : "MANUAL",
verifiedAt: result.matched ? new Date() : null
  7. Reputation পুনর্গণনা — recomputeFarmerReputation(farmerId) সাথে সাথে চলে, কারণ verification reputation-এর একটি উপাদান।
  8. Session সতেজ করা — frontend তারপর getMe() ডেকে localStorage-এর user object নতুন করে লেখে, যাতে dashboard সাথে সাথে unlock হয়।

10.4 Admin-এর manual review পথ

স্বয়ংক্রিয় যাচাই ব্যর্থ হলে profile PENDING থাকে এবং সে GET /api/v1/admin/farmers/verifications-এর তালিকায় চলে আসে (createdAt অনুসারে পুরোনো আগে — অর্থাৎ FIFO queue)।

সিদ্ধান্তEndpointডাটাবেসে কী লেখা হয়
ApprovePOST /api/v1/admin/farmers/{farmerId}/verification/approve VERIFIED · method = MANUAL · verifiedAt = now() · verifiedByAdminId = session.userId · audit action farmer_verification_approved

verifiedByAdminId একটি self-relation — User মডেলে verifiedFarmers FarmerProfile[] @relation("VerifiedByAdmin") হিসেবে ফিরে আসে। অর্থাৎ ডাটাবেসেই লেখা থাকে কোন admin কোন কৃষককে verify করেছেন।

12Farmer Reputation / Trust Score[[C12]]

12.1 কেন reputation দরকার?

Verification শুধু বলে “এই লোক সত্যিই কৃষক”। কিন্তু সে ভালো কৃষক কি না — সময়মতো পণ্য পৌঁছায় কি না, ক্রেতারা সন্তুষ্ট কি না — সেটি বলে না। reputation score সেই ফাঁকটি পূরণ করে।

  + reviewScore       * 0.40

);

14.3 Archive করলে ঠিক কী হয়?

DELETE /api/v1/products/{productId} — নাম DELETE হলেও এটি সারিটি মুছে না, শুধু status বদলায়:

export async function DELETE(request, { params }) {
  const session = requireUser(request);
  enforceRateLimit(request, "product-archive", { max: 20, windowMs: 60_000 });
  const product = await loadProduct(productId);
  assertOwnerOrAdmin(session, product);

  const archived = await prisma.product.update({
    where: { id: productId }, data: { status: "ARCHIVED" }, …
  });

  await recordAudit({ actorId: session.userId, actorRole: session.role,
    action: "product_archived", targetType: "Product", targetId: productId,
    metadata: { previousStatus: product.status, farmerId: product.farmerId } });

  return ok({ product: toPublicProduct(archived) }, { message: "Product archived" });
}
কীArchive-এর পরে অবস্থা
ডাটাবেস সারিঅক্ষত থাকে, শুধু status = ARCHIVED
Marketplaceআর দেখা যায় না
পুরোনো orderসম্পূর্ণ অক্ষত — nameSnapshot ও দামও OrderItem-এ আলাদা করে রাখা
Reviewঅক্ষত, reputation-এ গোনা চলতেই থাকে
TraceEventঅক্ষত; /trace/<id> পেজ কাজ করে
Wishlistসারিটি থেকে যায়, পণ্যটি wishlist পেজে দেখা যায় ছোট সীমাবদ্ধতা — archived বলে আলাদা চিহ্ন দেখানো হয় না
Cartআগে থেকে cart-এ থাকলে সারিটি থাকে, কিন্তু checkout-এ stock যাচাইয়ে আটকে যায় আংশিক
ছবিমুছে ফেলা হয় না — restore করলে ছবিও ফিরে আসে
Audit logএকটি product_archived এন্ট্রি লেখা হয়

14.4 Restore

Restore-এর জন্য আলাদা কোনো endpoint নেই; এটি সাধারণ একটি update: PATCH /api/v1/products/{id} with { status: "active" }। Admin console-এ archived পণ্যের সারিতে “Restore” বোতাম আসে; কৃষক নিজের edit form-এর Status drop-down থেকে আবার active বেছে নিতে পারেন।

toPublicTrace() সবসময় ছয়টি ধাপই ফেরত দেয়, কিন্তু যেটির কোনো event নেই সেটির completed: false ও timestamp: null। UI-তে সেটি ধূসর “Pending” হিসেবে দেখায়।

এটি একটি সৎ ডিজাইন

অনেক প্রজেক্টে খালি ধাপগুলোতে বানানো তারিখ বসিয়ে দেওয়া হয়, যাতে দেখতে ভালো লাগে। এখানে ইচ্ছাকৃতভাবে তা করা হয়নি — কোডের কমেন্টেই লেখা: “no fabricated timestamps.”

17.4 Blockchain আছে কি? — না

API response-এ দুটি ফিল্ড ইচ্ছাকৃতভাবে রাখা হয়েছে যাতে কেউ ভুল না বোঝে:

ledger_type: "database",
verification_note: "Traceability data is stored in the Fair Harvest database and
                    entered by the farmer. No blockchain or third-party ledger is used."

কোডের কমেন্টেও লেখা আছে — একটি verified_on_chain boolean রাখা হয়নি, কারণ সেটি একটি সাধারণ ডাটাবেস সারিকে “on-chain সত্য” বলে ভুলভাবে উপস্থাপন করত।

হোমপেজে একটি অসঙ্গতি — নিজে থেকেই স্বীকার করুন

হোমপেজের TrustCard-এ একটি স্থির “On-chain” লেখা chip আছে (app/page.js-এর <span className="chainChip">On-chain</span>)। এটি নিছক ডিজাইনের লেখা; এর পিছনে কোনো blockchain নেই এবং trace পেজ স্পষ্টভাবে উল্টো কথা বলে। বোর্ড ধরলে সরাসরি বলুন এটি একটি অবশিষ্ট UI লেবেল যা সরানো উচিত।

17.5 QR কোড

Response-এ qr_code: "qr_<productId>" নামে একটি স্ট্রিং আসে এবং trace পেজে সেটি লেখা হিসেবে দেখানো হয়। কোনো প্রকৃত QR ছবি তৈরি বা স্ক্যান করা হয় না — এটি একটি পরিচয়সূচক স্ট্রিং মাত্র।

18Cart System[[C18]]

18.1 Cart আর CartItem আলাদা কেন?

এটি database normalization-এর একটি পাঠ্যবই উদাহরণ। Cart হলো ধারক (প্রতি ব্যবহারকারীর ঠিক একটি), আর CartItem হলো তার ভিতরের প্রতিটি সারি। একটিতে সব রাখলে একই user-এর অনেক সারি লাগত এবং “cart খালি করা” বা “cart-এর মালিক কে” — এসব প্রশ্নের উত্তর জটিল হতো।

model Cart     { id  String @id  userId String @unique  items CartItem[] }
model CartItem { id  String @id  cartId String  productId String
                 quantityKg Float  unitPriceBdt Float  source CartItemSource
                 @@unique([cartId, productId, source]) }

18.2 তিনটি গুরুত্বপূর্ণ সিদ্ধান্ত

সিদ্ধান্তকারণ
userId @uniqueএকজন ব্যবহারকারীর একটির বেশি cart থাকতে পারবে না — ডাটাবেসই নিশ্চিত করে
unitPriceBdt CartItem-এ কপি করা cart-এ রাখার সময়ের দাম মনে রাখার জন্য। তবে একই পণ্য আবার যোগ করলে দাম নতুন করে বসানো হয় (unitPriceBdt: product.priceBdt)।
@@unique([cartId, productId, source]) একই পণ্য একই উৎস থেকে দুইবার সারি হিসেবে আসবে না — পরিমাণ যোগ হয়ে যাবে

18.3 CartItemSource

enum-এ তিনটি মান আছে: DIRECT, MEAL_PLAN, PRESCRIPTION। বাস্তবে UI থেকে শুধু DIRECT-ই তৈরি হয়; বাকি দুটি ভবিষ্যতের meal-plan ও ডাক্তারের prescription ফিচারের জন্য জায়গা রাখা আংশিক — enum আছে, UI নেই।

18.5 Backend যা করে

  1. প্রাপ্যতা যাচাই: if (!product || product.status !== "ACTIVE") → 404 "Product is not available"। অর্থাৎ archived বা out-of-stock পণ্য cart-এ যোগই করা যায় না।
  2. Cart তৈরি বা খুঁজে বের করা: prisma.cart.upsert() — না থাকলে বানায়, থাকলে ব্যবহার করে।
  3. যোগ না বৃদ্ধি: একই (cartId, productId, source) থাকলে quantityKg: existing.quantityKg + quantityKg, নাহলে নতুন সারি।
  4. মালিকানা যাচাই (item-এর ক্ষেত্রে): assertOwnedItem() দেখে item.cart.userId === userId কি না — না হলে 404 (403 নয়, যাতে অন্যের item-এর অস্তিত্ব ফাঁস না হয়)।

18.6 Frontend যা করে

components/cart/useCart.js একটি custom React hook যা cart-এর সব কাজ এক জায়গায় রাখে: { cart, loading, addItem, updateItem, removeItem, clear, refresh, isLoggedIn }। প্রতিটি পরিবর্তনের পর refresh() ডেকে server থেকে নতুন করে cart আনা হয় — অর্থাৎ subtotal সবসময় server-এর হিসাব, client-এর অনুমান নয়।

Login না থাকলে addItem() সরাসরি /auth/customer-এ পাঠিয়ে দেয়।

19Checkout ও Payment[[C19]]

সবচেয়ে জরুরি সত্য — প্রথমেই বলে নিচ্ছি

এই প্রজেক্টে কোনো প্রকৃত payment gateway নেই। bKash, Nagad, SSLCommerz, Stripe — কোনোটির সাথেই সংযোগ নেই। কোনো আসল টাকা কখনো লেনদেন হয় না। enum-এর নামই সেটি স্বীকার করে: PaymentMethod { COD, DEMO_CARD } এবং Payment.demoTransactionRef। এটিকে কখনোই “real payment integration” বলবেন না।

19.1 দুটি payment পদ্ধতি

পদ্ধতিUI-তে লেখাPayment.statusবাস্তবে কী ঘটে
DEMO_CARD“Demo card (charged instantly)” PAID, paidAt = now() কোনো কার্ড নম্বর চাওয়াই হয় না; কোড সরাসরি PAID লিখে দেয় SIMULATED
COD“Cash on delivery” PENDING, paidAt = null বাস্তবসম্মত — হাতে হাতে টাকা নেওয়ার ধারণা। তবে পরে PAID করার কোনো ব্যবস্থা নেই আংশিক

19.2 Checkout transaction — সবচেয়ে গুরুত্বপূর্ণ কোড

POST /api/v1/orders/{userId}/checkout — এখানে ছয়টি কাজ একটিমাত্র ডাটাবেস transaction-এর ভিতরে হয়। অর্থাৎ হয় সবগুলো হবে, নয়তো একটিও হবে না।

const order = await prisma.$transaction(async (tx) => {
  // ১. Order + সব OrderItem তৈরি (nameSnapshot ও দাম কপি করে)
  const created = await tx.order.create({ data: { userId, totalBdt: total, …,
        items: { create: cart.items.map(item => ({ productId, farmerId,
                 nameSnapshot: item.product.name, quantityKg, unitPriceBdt, lineTotalBdt })) },
        statusEvents: { create: [{ status: "PENDING", note: "Order placed" }] } } });

  // ২. প্রতিটি পণ্যের মজুদ কমানো
  for (const item of cart.items)
    await tx.product.update({ where: { id: item.productId },
                              data: { quantityKg: { decrement: item.quantityKg } } });

  // ৩. Payment সারি
  await tx.payment.create({ data: { orderId: created.id, method, amountBdt: total,
        status: isDemoCardPaid ? "PAID" : "PENDING",
        demoTransactionRef: `DEMO-${created.id.slice(0, 8)}`,
        paidAt: isDemoCardPaid ? new Date() : null } });

  // ৪. পুরস্কার পয়েন্ট
  await tx.rewardsLedger.create({ data: { userId, points: 20, reason: "Healthy purchase" } });

  // ৫. Cart খালি করা
  await tx.cartItem.deleteMany({ where: { cartId: cart.id } });

  return created;
});
Transaction কেন? — ভাইভার চমৎকার উত্তর

“ধরুন order তৈরি হলো, কিন্তু stock কমানোর ঠিক আগে server বন্ধ হয়ে গেল। তাহলে একটি order থাকত যার জন্য কোনো stock কাটা হয়নি — হিসাব চিরতরে ভুল হয়ে যেত। $transaction নিশ্চিত করে যে পাঁচটি কাজই একসাথে সফল হবে, নাহলে ডাটাবেস আগের অবস্থায় ফিরে যাবে (rollback)। এটিকে বলে atomicity — ACID-এর A।”

20.1 পাঁচটি OrderStatus

Statusঅর্থকখন বসে

  prisma.orderItem.findFirst({

  prisma.review.findUnique({ where: { customerId_productId: { customerId, productId } } })

// lib/server/reviewEligibility.js  (pure — টেস্ট করা যায়)
export function decideEligibility({ deliveredOrderItem, alreadyReviewed }) {
  if (alreadyReviewed)     return { eligible: false, reason: "already_reviewed" };
  if (!deliveredOrderItem) return { eligible: false, reason: "not_purchased" };
  return { eligible: true, orderItemId: deliveredOrderItem.id };
}

Admin-এর হাতে অনেক ক্ষমতা — কারও অ্যাকাউন্ট বন্ধ করা, কারও review লুকিয়ে ফেলা, কাউকে verified করা। এই ক্ষমতার সাথে জবাবদিহি থাকা দরকার। Audit log সেই জবাবদিহির খাতা: কে, কখন, কার উপর, কী করল — সব লেখা থাকে।

27.2 মডেল ও একটি অস্বাভাবিক সিদ্ধান্ত

model AuditLog {
  id         String   @id @default(cuid())
  actorId    String   // কে করল (plain string, FK নয়)
  actorRole  String
  action     String   // যেমন "farmer_verification_approved"
  targetType String   // "FarmerProfile" | "User" | "Review" | "Product"

  metadata   String?  // JSON.stringify করা অতিরিক্ত তথ্য

  @@index([targetType, targetId])
  @@index([createdAt])
}
এখানে ইচ্ছাকৃতভাবে কোনো Foreign Key নেই — কেন?

কোডের কমেন্টেই উত্তরটি লেখা আছে: “an audit record must survive even if the target row is later deleted.” যদি actorId একটি FK হতো, তাহলে সেই admin-এর অ্যাকাউন্ট মুছে গেলে audit সারিটিও cascade-এ মুছে যেত বা লেখা যেত না। অর্থাৎ যে জিনিসটির পুরো উদ্দেশ্যই “প্রমাণ রেখে দেওয়া”, সেটিই হারিয়ে যেত। তাই id গুলো নিছক string snapshot হিসেবে রাখা হয়েছে।

28Rate Limiting ও সামগ্রিক নিরাপত্তা[[C28]]

28.1 Rate limiting কী এবং কেন?

একই ব্যক্তি অল্প সময়ে অসংখ্যবার একই কাজ করার চেষ্টা করলে সেটি আটকে দেওয়া। উদ্দেশ্য — পাসওয়ার্ড অনুমান করার চেষ্টা (brute force), অসংখ্য ভুয়া অ্যাকাউন্ট তৈরি, আর storage ভরে ফেলা ঠেকানো।

28.2 বাস্তবায়ন — sliding window

const buckets = new Map();              // key → timestamp[]

function clientKey(request, scope) {
  const forwarded = request.headers.get("x-forwarded-for");
  const ip = forwarded ? forwarded.split(",")[0].trim() : "unknown";
  return `${scope}:${ip}`;
}

export function enforceRateLimit(request, scope, { max = 10, windowMs = 60_000 } = {}) {
  const now = Date.now();
  const recent = (buckets.get(key) || []).filter(ts => now - ts < windowMs);
  if (recent.length >= max) throw new ApiError("Too many requests — please try again shortly", 429);
  recent.push(now);
  buckets.set(key, recent);
}

“Sliding window” মানে — শেষ ৬০ সেকেন্ডের ভিতরে পড়া timestamp গোনা হয়, ঘড়ির নির্দিষ্ট মিনিট নয়। ফলে মিনিট বদলের মুহূর্তে দ্বিগুণ request পাঠানোর ফাঁক থাকে না।

28.5 যা এখনো নেই Future

  • HttpOnly cookie — টোকেন localStorage-এ থাকায় XSS হলে সেটি চুরি হতে পারে। HttpOnly cookie নিরাপদ হতো (তবে তখন CSRF ব্যবস্থা লাগত)।
  • Refresh token — ২ ঘণ্টা পর আবার login করতে হয়।
  • Token revocation — logout বা suspend করলেও পুরোনো token মেয়াদ শেষ না হওয়া পর্যন্ত বৈধ।
  • শক্তিশালী পাসওয়ার্ড নীতি — শুধু ন্যূনতম ৬ অক্ষর।
  • Email যাচাই ও পাসওয়ার্ড পুনরুদ্ধার — কোনোটিই নেই।
  • 2FA, CSP header, account lockout — নেই।
  • বিতরণকৃত rate limiting — Redis ইত্যাদি নেই।

30.1 ORM কী? কেন Prisma?

ORM (Object-Relational Mapping) — যে স্তরটি ডাটাবেসের সারি (row) আর কোডের object-এর মধ্যে অনুবাদক হিসেবে কাজ করে। হাতে SQL লেখার বদলে আমরা লিখি prisma.product.findMany({ where: { status: "ACTIVE" } }), আর Prisma সেটিকে নিরাপদ SQL-এ রূপান্তর করে।

সুবিধাব্যাখ্যা
Single source of truthএকটি schema.prisma থেকেই ডাটাবেস, migration ও TypeScript টাইপ — সব তৈরি হয়
SQL injection প্রতিরোধPrisma সবসময় parameterized query তৈরি করে; ব্যবহারকারীর লেখা কখনো SQL-এর অংশ হয় না
Auto-complete ও টাইপভুল ফিল্ডের নাম লিখলে সম্পাদকেই ধরা পড়ে
Migration ইতিহাসপ্রতিটি schema পরিবর্তন একটি SQL ফাইল হিসেবে git-এ সংরক্ষিত
Relation queryinclude: { farmer: { include: { user: true } } } — জটিল join এক লাইনে

// lib/api.js — একটিই request helper
const API_ROOT = process.env.NEXT_PUBLIC_API_URL || "/api/v1";

async function request(path, options = {}) {
  const headers = { "Content-Type": "application/json", ...(options.headers || {}) };
  if (typeof window !== "undefined") {
    const token = window.localStorage.getItem("fairHarvestToken");
    if (token) headers.Authorization = `Bearer ${token}`;      // স্বয়ংক্রিয়ভাবে যুক্ত
  }
  const response = await fetch(`${API_ROOT}${path}`, { ...options, headers, cache: "no-store" });
  const body = await response.json().catch(() => ({ success: false, message: "Invalid API response" }));
  if (!response.ok) {
    if (response.status === 401 && typeof window !== "undefined") window.location.href = "/auth";
    throw new Error(body.message || "Request failed");
  }
  return body.data;      // খাম খুলে শুধু data ফেরত
}

এই একটিমাত্র ফাংশনের উপর ৫০-এর বেশি নামকরা helper তৈরি করা হয়েছে (getProducts, checkout, archiveProduct …), তাই কোনো component-কে কখনো URL বা header নিয়ে ভাবতে হয় না।

cache: "no-store" গুরুত্বপূর্ণ — নাহলে Next.js পুরোনো উত্তর cache করে রাখত এবং cart বা order-এর সংখ্যা পুরোনো দেখাত।

A. কৃষক নিবন্ধন

Form (/auth/farmer, mode=register) → register() → POST /auth/register
  → rate limit 6/min → Zod (role ∈ consumer|farmer) → email unique? (409 না হলে)
  → bcrypt.hash(password, 10) → User.create + FarmerProfile.create({})
  → signToken() → { access_token, user } → localStorage → /farmer/dashboard

B. Farmer Card যাচাই

Form (/farmer/verify) → verifyFarmerCard() → POST /farmers/{id}/verify
  → rate limit 8/min → requireOwnerOrRole → Zod
  → verifyFarmerCard() → demoRegistryProvider → GovFarmerCardRecord lookup
  → FarmerProfile.update(status/method/verifiedAt) → recomputeFarmerReputation()
  → getMe() → localStorage সতেজ → dashboard unlock

C. Admin অনুমোদন

/admin/verification → approve() → POST /admin/farmers/{id}/verification/approve
  → requireRole(["ADMIN"]) → FarmerProfile.update(VERIFIED, MANUAL, verifiedByAdminId)
  → recordAudit("farmer_verification_approved") → load() → queue রিফ্রেশ

D. ছবি আপলোড ও পণ্য তৈরি

file input → uploadProductImage(file) → POST /uploads/product-image (multipart)
  → requireUser → rate limit 20/min → VERIFIED farmer? → validateImageUpload(MIME, size)
  → byte দ্বিতীয়বার যাচাই → buildStorageKey(products/<uuid>.jpg)
  → putObject() → [local disk | Vercel Blob] → { image_url }
                                   │
Add product form ─────────────────►│ POST /products { …, image_url }
  → verification gate → Product.create → 201 → তালিকা রিফ্রেশ

E. Marketplace ব্রাউজিং

useEffect([filters]) → getProducts(filters) → GET /products?category=&min_trust=&max_price=
  → where তৈরি (farmer_id না থাকলে status=ACTIVE) → findMany(include farmer.user)
  → orderBy trustScore desc → toPublicProduct[] → setProducts → card grid
  → (search box শুধু client-side ফিল্টার করে)

F. Cart-এ যোগ

AddToCartButton → useCart.addItem() → login? না হলে /auth/customer
  → POST /cart/{userId}/items → requireOwnerOrRole
  → product ACTIVE? (না হলে 404) → cart.upsert
  → একই (cart, product, source) থাকলে quantity যোগ, নাহলে নতুন CartItem
  → refresh() → GET /cart/{userId} → subtotal server-এ গোনা

G. Checkout, Payment ও Order

/checkout submit → checkout(user.id, {address, fee, method}) → POST /orders/{id}/checkout
  → requireOwnerOrRole → Zod → cart খালি? (400) → প্রতিটি item-এর stock যাচাই (409)
  → $transaction:
       Order.create + OrderItem[] (nameSnapshot, দাম কপি) + OrderStatusEvent(PENDING)
       প্রতিটি Product.quantityKg decrement
       Payment.create (DEMO_CARD → PAID, COD → PENDING)
       RewardsLedger.create(+20)
       CartItem.deleteMany
  → 201 → window.location = /orders/{orderId}

H. Order status পরিবর্তন

Admin drop-down বা কৃষক → PATCH /orders/{orderId}/status
  → requireUser → ADMIN? নাহলে এই order-এ নিজের item আছে কি? (403)
  → Zod (৫টি status) → Order.update + নতুন OrderStatusEvent
  → DELIVERED বা CANCELLED হলে: Set(farmerIds).map(recomputeFarmerReputation)

I. Review ও Reputation

ReviewsSection submit → POST /reviews
  → requireUser → role CONSUMER? (403) → Zod (rating 1–5)
  → Product আছে? (404) → getReviewEligibility(customerId, productId)
       ├─ DELIVERED OrderItem খোঁজা

const REQUEST_TIMEOUT_MS = 5000;
function fetchWithTimeout(input, init = {}) {
  return fetch(input, { ...init, signal: AbortSignal.timeout(REQUEST_TIMEOUT_MS) });

  if (isServer && !hasAbsoluteBase) return fallback;   // build-এ ঝুলে থাকা ঠেকায়

37Error Handling[[C37]]

37.1 কেন্দ্রীয় ব্যবস্থা

প্রতিটি route handler-এর ভিতরের কোড handleRoute()-এ মোড়ানো। ফলে কোথাও try/catch লিখতে হয় না, আর ত্রুটির উত্তরের আকারও সব জায়গায় এক।

export class ApiError extends Error {
  constructor(message, status = 400) { super(message); this.status = status; }
}

export async function handleRoute(fn) {
  try { return await fn(); }
  catch (error) {
    if (error instanceof ApiError) return fail(error.message, { status: error.status });
    console.error(error);                                   // সার্ভারের লগে বিস্তারিত
    return fail("Internal server error", { status: 500 });  // ক্লায়েন্টকে শুধু এইটুকু
  }
}
এখানে একটি নিরাপত্তা সিদ্ধান্ত লুকানো আছে

অপ্রত্যাশিত ত্রুটির বিস্তারিত (stack trace, SQL, ফাইলের পথ) কখনো ব্রাউজারে পাঠানো হয় না। সেগুলো শুধু server log-এ যায়। নাহলে আক্রমণকারী ত্রুটির বার্তা থেকে ডাটাবেসের গঠন বুঝে ফেলতে পারত।

Next.js 15 App Router-এ একটিই deployment, যা UI এবং /api/v1-এর ৬৪টি REST endpoint দুটোই পরিবেশন করে। Prisma ORM দিয়ে PostgreSQL (Neon), JWT authentication, Vercel-এ deploy, ছবি Vercel Blob-এ।

আরও প্রশ্ন করলে — “তাহলে অন্য সাইট থেকে আলাদা কী?” → verification gate, purchase-gated review এবং soft delete-এর উদাহরণ দিন।

প্রশ্ন ২: এই প্রজেক্টটি কেন বেছে নিলেন?

সহজ উত্তর
বাংলাদেশের কৃষক মধ্যস্বত্বভোগীর কারণে ন্যায্য দাম পান না, আর শহরের ক্রেতা জানেন না তার খাবার কোথা থেকে এসেছে। একটি প্রযুক্তিগত সমাধান দুটি সমস্যাই একসাথে ধরতে পারে।

বিস্তারিত
শুধু একটি অনলাইন দোকান বানালে সমস্যা সমাধান হয় না — কারণ মূল সমস্যা বিশ্বাস। তাই আমি ইচ্ছাকৃতভাবে verification, reputation ও traceability-কে প্রজেক্টের কেন্দ্র বানিয়েছি, e-commerce অংশকে নয়।

আরও প্রশ্ন করলে — “এটি কি বাস্তবে ব্যবহার করা যাবে?” → “মূল কাঠামো প্রস্তুত; বাস্তব ব্যবহারের জন্য প্রকৃত payment gateway, ডেলিভারি সংযোগ ও সরকারি API দরকার — অধ্যায় 42-এ পথও বলা আছে।”

প্রশ্ন ৩: আপনার প্রজেক্টের সবচেয়ে গুরুত্বপূর্ণ অংশ কোনটি?

সহজ উত্তর
Farmer verification gate। কারণ পুরো প্ল্যাটফর্মের প্রতিশ্রুতিই হলো “verified কৃষকের কাছ থেকে কিনছেন”।

Technical
POST /api/v1/products-এ একটি শর্ত: if (farmer.verificationStatus !== "VERIFIED") throw new ApiError(…, 403)। এই একটি লাইনই পুরো ব্যবসায়িক নিয়মটি প্রয়োগ করে। একই নিয়ম ছবি আপলোডেও আছে।

কোথায় app/api/v1/products/route.js

প্রশ্ন ৪: কতটুকু কোড আপনি নিজে লিখেছেন?

সহজ উত্তর
সম্পূর্ণ application কোড — schema, ৬৪টি API handler, সব React পেজ ও component, এবং SDK প্যাকেজটিও।

বিস্তারিত
বাইরের লাইব্রেরি হিসেবে ব্যবহার করেছি Next.js, React, Prisma, Zod, bcryptjs, jsonwebtoken, lucide-react ও @vercel/blob। CSS কোনো framework ছাড়া হাতে লেখা।

B. প্রযুক্তি নির্বাচন

প্রশ্ন ৫: Next.js কেন? শুধু React ব্যবহার করলে কী হতো?

সহজ উত্তর
শুধু React হলে API-র জন্য আলাদা একটি Express server লাগত। Next.js-এ frontend ও backend একই প্রজেক্টে থাকে।

বিস্তারিত
এতে চারটি সুবিধা পেয়েছি — (১) একবারে deploy, (২) CORS-এর জটিলতা নেই কারণ same-origin, (৩) Server Component দিয়ে SEO-বান্ধব HTML, (৪) একই কোড দুই দিকে ভাগ করা যায়।

Technical
App Router-এ app/api/v1/**/route.js ফাইলগুলোই backend। প্রতিটি HTTP method একটি export করা async function।

আরও প্রশ্ন করলে — “Server আর Client Component-এর পার্থক্য?” → “Server Component-এর JS ব্রাউজারে যায় না, তাই হালকা ও SEO-বান্ধব; কিন্তু সেখানে state বা onClick রাখা যায় না। আমার হোমপেজ, product detail ও trace পেজ server component; dashboard ও form-গুলো client।”

প্রশ্ন ৬: Prisma কেন? সরাসরি SQL লিখলে কী সমস্যা?

সহজ উত্তর
Prisma একটি ORM — schema থেকেই ডাটাবেস, migration ও query-র টাইপ সব তৈরি হয়, আর SQL injection-এর ঝুঁকি কমে।

Technical
Prisma সবসময় parameterized query তৈরি করে, তাই ব্যবহারকারীর লেখা কখনো SQL-এর অংশ হয় না। include দিয়ে relation একসাথে আনা যায়, আর $transaction দিয়ে atomic কাজ করা যায় — আমার checkout ঠিক এটাই ব্যবহার করে।

আরও প্রশ্ন করলে — “ORM-এর অসুবিধা?” → “খুব জটিল query-তে হাতে লেখা SQL দ্রুততর হতে পারে, এবং ORM কী SQL তৈরি করছে তা না জানলে N+1 সমস্যা হতে পারে। আমার প্রজেক্টে query সরল, তাই সমস্যা হয়নি।”

প্রশ্ন ৭: PostgreSQL কেন? MongoDB বা MySQL নয় কেন?

সহজ উত্তর
আমার ডেটা সম্পূর্ণ relational — user, farmer, product, order, review সব একে অন্যের সাথে যুক্ত। তাই relational database-ই স্বাভাবিক পছন্দ।

বিস্তারিত
MongoDB হলে foreign key, cascade, RESTRICT আর transaction-এর নিশ্চয়তা কোডে হাতে লিখতে হতো। আমার soft delete-এর পুরো ভিত্তিই OrderItem → Product-এর RESTRICT সম্পর্ক। PostgreSQL বেছে নেওয়ার বিশেষ কারণ — native enum সমর্থন (আমার ১৩টি enum আছে) এবং Neon-এর serverless free tier।

আরও প্রশ্ন করলে — “SQLite থেকে সরালেন কেন?” → “SQLite একটি ফাইল; Vercel-এর serverless ফাইল সিস্টেম read-only ও ক্ষণস্থায়ী, তাই production-এ ডেটা টিকত না।”

প্রশ্ন ৮: JWT কেন? Session কেন নয়?

সহজ উত্তর
JWT stateless — server-এ কোনো session টেবিল রাখতে হয় না, তাই serverless পরিবেশে ভালো কাজ করে।

Technical
Vercel-এ প্রতিটি request আলাদা function instance-এ চলতে পারে, যাদের মধ্যে কোনো ভাগ করা memory নেই। Session-ভিত্তিক auth-এ প্রতিবার ডাটাবেসে গিয়ে session দেখতে হতো। JWT-তে signature যাচাই করেই পরিচয় পাওয়া যায় — কোনো DB call ছাড়াই।

আরও প্রশ্ন করলে — “JWT-র অসুবিধা?” → “বাতিল করা কঠিন। আমার প্রজেক্টে logout শুধু localStorage মুছে; token তার ২ ঘণ্টার মেয়াদ পর্যন্ত প্রযুক্তিগতভাবে বৈধ থাকে। সমাধান হতো refresh token বা blacklist।” — এই স্বীকারোক্তিটি বোর্ড পছন্দ করেন।

প্রশ্ন ৯: REST কেন, GraphQL নয় কেন?

সহজ উত্তর
REST সরল, সবাই জানে, আর Next.js-এর route handler-এর সাথে স্বাভাবিকভাবে মেলে।

বিস্তারিত
GraphQL তখন লাগে যখন ক্লায়েন্টভেদে ভিন্ন ভিন্ন আকারের ডেটা দরকার। আমার ক্ষেত্রে ক্লায়েন্ট একটিই। তাছাড়া GraphQL-এ caching ও rate limiting বসানো তুলনামূলক জটিল।

প্রশ্ন ১০: Vercel কেন?

সহজ উত্তর
Vercel-ই Next.js-এর নির্মাতা, তাই App Router-এর সব সুবিধা সেখানে সরাসরি কাজ করে; সাথে git push করলেই স্বয়ংক্রিয় deploy।

Technical
Preview deployment (প্রতিটি branch-এর আলাদা URL), স্বয়ংক্রিয় HTTPS, CDN, environment variable ব্যবস্থাপনা এবং Vercel Blob — সব একই জায়গায়। build কমান্ডে prisma migrate deploy রাখায় প্রতিটি deploy-এ ডাটাবেসও হালনাগাদ হয়ে যায়।

প্রশ্ন ১১: Vercel Blob কেন? ছবি ডাটাবেসে রাখলেন না কেন?

সহজ উত্তর
ছবির bytes ডাটাবেসে রাখলে ডাটাবেস দ্রুত বড় হয়ে ধীর হয়ে যেত। তাই ছবি object storage-এ, আর ডাটাবেসে শুধু URL।

Technical
Production-এ local disk ব্যবহার করা সম্ভবই নয় — serverless ফাইল সিস্টেম /tmp ছাড়া read-only এবং প্রতিটি invocation-এর পর মুছে যায়। আমার প্রজেক্টে বাস্তবে এই ত্রুটিটি এসেছিল: ENOENT … mkdir '/var/task/…/storage'। সমাধান — STORAGE_PROVIDER=object।

C. Authentication ও Authorization

প্রশ্ন ১২: Authentication আর Authorization-এর পার্থক্য কী?

সহজ উত্তর
Authentication = “তুমি কে?” (পরিচয় প্রমাণ)। Authorization = “তুমি কী করতে পারবে?” (অধিকার যাচাই)।

Technical
আমার কোডে দুটি আলাদা জায়গায়: authentication হয় /auth/login-এ bcrypt দিয়ে পাসওয়ার্ড মিলিয়ে JWT দেওয়ার সময়; authorization হয় প্রতিটি route-এ requireRole বা requireOwnerOrRole দিয়ে।

প্রশ্ন ১৩: পাসওয়ার্ড কীভাবে সংরক্ষণ করেন?

সহজ উত্তর
কখনোই plain text-এ নয়। bcrypt দিয়ে hash করে রাখি, cost factor ১০।

Technical
bcrypt.hash(password, 10)। bcrypt নিজে থেকেই প্রতিটি পাসওয়ার্ডের জন্য আলাদা salt তৈরি করে, তাই একই পাসওয়ার্ডের দুজন ব্যবহারকারীর hash আলাদা হয় — rainbow table আক্রমণ কাজ করে না। যাচাইয়ের সময় bcrypt.compare(), কারণ hash থেকে মূল পাসওয়ার্ড ফেরত পাওয়া যায় না।

আরও প্রশ্ন করলে — “cost 10 মানে কী?” → “২¹⁰ = ১০২৪ বার hashing round। ইচ্ছাকৃতভাবে ধীর, যাতে আক্রমণকারী সেকেন্ডে লক্ষ লক্ষ পাসওয়ার্ড পরীক্ষা করতে না পারে।”

প্রশ্ন ১৪: JWT-তে কী কী থাকে? কেউ কি সেটি পাল্টে ফেলতে পারে?

সহজ উত্তর
ভিতরে থাকে user id, role, email আর মেয়াদ। কেউ পাল্টালে signature মেলে না, তাই server সঙ্গে সঙ্গে বাতিল করে দেয়।

Technical
jwt.sign({ sub: user.id, role, email }, JWT_SECRET, { expiresIn: "2h" }) — HS256 অ্যালগরিদম। Payload base64-এ থাকে, তাই কেউ পড়তে পারে; কিন্তু বদলাতে পারে না, কারণ signature তৈরি করতে JWT_SECRET লাগে।

আরও প্রশ্ন করলে — “তাহলে payload-এ গোপন তথ্য রাখা যায়?” → “না, একেবারেই নয়। তাই আমি শুধু id, role আর email রেখেছি।”

প্রশ্ন ১৫: টোকেন localStorage-এ রাখা কি নিরাপদ?

সহজ উত্তর
সম্পূর্ণ নিরাপদ নয় — XSS হলে JavaScript সেটি পড়তে পারে। HttpOnly cookie বেশি নিরাপদ হতো।

বিস্তারিত
এটি আমি জেনেবুঝেই করেছি: localStorage সহজ এবং CSRF-মুক্ত। HttpOnly cookie নিলে XSS থেকে রক্ষা পেতাম, কিন্তু তখন CSRF token লাগত। বাস্তব production-এ আমি HttpOnly cookie + refresh token ব্যবহার করতাম — এটি অধ্যায় 42-এ future scope হিসেবে লেখা আছে।

টিপ এই প্রশ্নে “হ্যাঁ নিরাপদ” বলবেন না। trade-off বুঝে উত্তর দিলে নম্বর বেশি।

প্রশ্ন ১৬: ভুল পাসওয়ার্ড আর ভুল ইমেইল — দুটোতেই একই বার্তা কেন?

সহজ উত্তর
যাতে আক্রমণকারী বুঝতে না পারে কোন ইমেইলটি সিস্টেমে আছে।

Technical
এটিকে বলে user enumeration প্রতিরোধ। “এই ইমেইল নেই” বললে আক্রমণকারী আগে বৈধ ইমেইলের তালিকা বানিয়ে তারপর শুধু সেগুলোতে পাসওয়ার্ড অনুমান করত। আমার কোডে তিনটি ক্ষেত্রেই একই বার্তা — ব্যবহারকারী নেই, suspended, বা পাসওয়ার্ড ভুল।

প্রশ্ন ১৭: আমি যদি URL-এ অন্যের userId বসিয়ে দিই?

সহজ উত্তর
403 পাবেন। প্রতিটি route মালিকানা যাচাই করে।

Technical
এই আক্রমণকে বলে IDOR। requireOwnerOrRole(request, userId, ["ADMIN"]) JWT-র session.userId-এর সাথে URL-এর id মিলিয়ে দেখে। আর wishlist, farmer/orders ও farmer/earnings-এ আমি URL-এ id রাখিইনি — সেগুলো সবসময় session থেকে নেওয়া, তাই আক্রমণের সুযোগই নেই।

প্রশ্ন ১৮: RoleGuard দিয়েই তো পেজ আটকানো আছে — সেটাই কি যথেষ্ট নয়?

সহজ উত্তর
না। RoleGuard শুধু UI-এর সুবিধা। কেউ সরাসরি API-তে request পাঠালে সেটি কোনো কাজেই আসত না।

Technical
client-side যেকোনো কিছু ব্যবহারকারী বদলে ফেলতে পারে — JavaScript বন্ধ করা যায়, বা curl দিয়ে সরাসরি endpoint-এ যাওয়া যায়। তাই আসল সিদ্ধান্ত সবসময় server-এ। আমার RoleGuard ফাইলের কমেন্টেই লেখা আছে: “This is a user-experience guard only… that server check is what actually secures the data.”

প্রশ্ন ১৯: কেউ কি নিজেকে admin বানিয়ে register করতে পারবে?

সহজ উত্তর
না। register schema-তে role হিসেবে শুধু consumer ও farmer অনুমোদিত।

Technical

প্রশ্ন ২০: JWT_SECRET ফাঁস হয়ে গেলে কী হবে?

সহজ উত্তর
যে কেউ নিজের জন্য admin token বানিয়ে ফেলতে পারত — তাই এটি সবচেয়ে গুরুত্বপূর্ণ গোপন মান।

Technical
সেজন্যই এটি কখনো কোডে লেখা হয়নি, শুধু environment variable-এ। এবং production-এ এটি না থাকলে অ্যাপ ইচ্ছাকৃতভাবে চালু হতেই অস্বীকার করে — নাহলে development-এর জানা ডিফল্ট secret দিয়ে যে কেউ token বানাতে পারত।

D. Farmer Verification ও Farmer Card

প্রশ্ন ২১: Farmer Card verification কীভাবে কাজ করে?

সহজ উত্তর
কৃষক Farmer Card নম্বর, NID আর নাম দেন। সিস্টেম সেটি একটি registry-তে খুঁজে দেখে। তিনটিই মিললে সঙ্গে সঙ্গে verified; না মিললে admin হাতে দেখেন।

Technical
POST /farmers/{id}/verify → rate limit ৮/মিনিট → requireOwnerOrRole → Zod → verifyFarmerCard() → GovFarmerCardRecord.findUnique({ cardNumber }) → status ACTIVE কি না → NID ও normalize করা নাম মিলিয়ে দেখা → মিললে matched: true, confidence: 0.98 → profile VERIFIED → recomputeFarmerReputation()।

কোথায় lib/server/verification/demoRegistryProvider.js

প্রশ্ন ২২: এটি কি সত্যিকারের সরকারি API?

সহজ উত্তর
না। এটি একটি demo registry — আমার নিজের ডাটাবেসের GovFarmerCardRecord টেবিল, যেখানে seed দিয়ে ৮টি নমুনা কার্ড রাখা।

বিস্তারিত
বাংলাদেশে শিক্ষার্থীর জন্য উন্মুক্ত কোনো Farmer Card API নেই। তাই আমি provider abstraction বানিয়েছি: demoRegistryProvider.js এখন চলে, আর officialGovApiProvider.js লেখা আছে সঠিক request/response আকারে। ভবিষ্যতে আসল API পেলে শুধু VERIFICATION_PROVIDER=official করে দিলেই হবে — route, schema বা frontend-এর একটি লাইনও বদলাতে হবে না।

টিপ এই প্রশ্নটি প্রায় নিশ্চিতভাবে আসবে। সরাসরি “না” বলে তারপর abstraction-এর কথা বলুন — এতে দুর্বলতা শক্তিতে বদলে যায়।

প্রশ্ন ২৩: কার্ড নম্বর ঠিক কিন্তু নাম ভুল হলে?

সহজ উত্তর
matched: false, confidence ০.৫, কারণ details_mismatch। profile PENDING থাকে এবং admin-এর কাছে চলে যায়।

Technical
নাম মেলানোর আগে trim().toLowerCase().replace(/\s+/g, " ") করা হয়, তাই বাড়তি স্পেস বা বড়-ছোট হরফে সমস্যা হয় না। তবে বানান ভুল হলে মিলবে না — fuzzy matching নেই।

প্রশ্ন ২৪: verified না হলে কৃষক কী করতে পারেন না?

সহজ উত্তর
পণ্য তালিকাভুক্ত করতে পারেন না এবং ছবিও আপলোড করতে পারেন না। login, dashboard দেখা ও verification জমা দেওয়া — এইটুকুই।

Technical
দুই জায়গায় gate: products/route.js-এর POST এবং uploads/product-image/route.js। দ্বিতীয়টি রাখার কারণ — নাহলে কেউ প্ল্যাটফর্মকে ফ্রি file hosting হিসেবে ব্যবহার করত।

ডেমোতে দেখান Rahim (verified) ও Karim (pending) — একই dashboard সম্পূর্ণ আলাদা দেখায় (চিত্র 28 ও 29)।

প্রশ্ন ২৫: Admin-এর সিদ্ধান্ত কোথাও রেকর্ড হয়?

সহজ উত্তর
হ্যাঁ। দুই জায়গায় — FarmerProfile.verifiedByAdminId-এ কোন admin, আর AuditLog-এ সম্পূর্ণ ঘটনা।

Technical
verifiedByAdminId একটি self-relation — User মডেলে verifiedFarmers FarmerProfile[] @relation("VerifiedByAdmin")। AuditLog-এ action হয় farmer_verification_approved নয়তো _rejected।

E. Reputation

প্রশ্ন ২৬: Reputation score কীভাবে হিসাব হয়? সূত্রটি বলুন।

সহজ উত্তর
তিনটি সংকেতের weighted average — verification ৩৫%, review rating ৪০%, delivery সম্পূর্ণতা ২৫%।

Technical
Score = clamp(0.35 × Sver + 0.40 × Srev + 0.25 × Sdel)
যেখানে Sver = VERIFIED→90, PENDING→60, REJECTED→30; Srev = (গড় rating ÷ 5) × 100, review না থাকলে 70; Sdel = (delivered ÷ মোট order item) × 100, order না থাকলে 75।

উদাহরণ (আমার চালু সিস্টেম থেকে)
Rahim Uddin — verified (90), একটি ৫-তারা review (100), একটি DELIVERED item (100)। → 90×0.35 + 100×0.40 + 100×0.25 = 31.5 + 40 + 25 = 96.5 → 97 → badge “Trusted Seller”।

কোথায় lib/server/reputation.js

প্রশ্ন ২৭: নতুন কৃষক, যার কোনো review নেই — তার score কত?

সহজ উত্তর
review ও delivery-র জন্য নিরপেক্ষ ভিত্তি ধরা হয় (70 ও 75), শূন্য নয়।

বিস্তারিত
শূন্য ধরলে একজন সৎ নতুন কৃষক শুরুতেই “খারাপ” দেখাতেন, অথচ তিনি কিছু ভুল করেননি। এটি একটি সচেতন ন্যায্যতার সিদ্ধান্ত — কোডের কমেন্টেও লেখা আছে। তাই নতুন verified কৃষকের score হয় 90×0.35 + 70×0.40 + 75×0.25 = 31.5 + 28 + 18.75 = 78 → “Reliable Farmer”।

প্রশ্ন ২৮: Score কখন আপডেট হয়?

সহজ উত্তর
চারটি ঘটনায় — নতুন review, verification সিদ্ধান্ত, order DELIVERED/CANCELLED হওয়া, এবং admin কোনো review hide/republish করলে।

Technical
দুটি আলাদা ফাংশন আছে: getFarmerReputationBreakdown() শুধু গণনা করে (GET route-এ ব্যবহৃত, কিছু লেখে না), আর recomputeFarmerReputation() গণনা করে ডাটাবেসে লিখে রাখে। GET request-এ ডাটাবেস লেখা উচিত নয় বলেই এই দুটি আলাদা।

প্রশ্ন ২৯: প্রতিবার গণনা না করে ডাটাবেসে লিখে রাখেন কেন?

সহজ উত্তর
কারণ marketplace-এর প্রতিটি কার্ডে score দেখাতে গেলে প্রতিটি কৃষকের জন্য আলাদা করে review ও order গোনা লাগত — অনেক query।

Technical
এটিকে বলে materialized value বা computed-column caching। খরচ হলো — event-এ recompute করতে ভুলে গেলে মান পুরোনো হয়ে যেতে পারে। তাই আমি ঠিক চারটি জায়গায় recompute কল রেখেছি এবং সেগুলো নথিভুক্ত।

প্রশ্ন ৩০: Product-এর trust score আর farmer-এর reputation কি একই?

সহজ উত্তর
না, সম্পূর্ণ আলাদা। Farmer reputation স্বয়ংক্রিয়ভাবে গণনা হয়; Product.trustScore এখনো একটি স্থির মান (ডিফল্ট ৮০)।

সৎ স্বীকারোক্তি
marketplace কার্ডে যে “91%” দেখা যায় সেটি seed-এ হাতে বসানো। কোনো API এটি স্বয়ংক্রিয়ভাবে বদলায় না। ভবিষ্যতে trace-এর সম্পূর্ণতা, সেই পণ্যের review ও কৃষকের reputation মিলিয়ে এটিও গণনা করা যেত।

F. পণ্য, Archive ও Soft Delete

প্রশ্ন ৩১: পণ্য delete করলে কী হয়?

সহজ উত্তর
ডাটাবেস থেকে মুছে যায় না — শুধু status হয়ে যায় ARCHIVED। একে বলে soft delete।

Technical
Endpoint-এর নাম DELETE হলেও ভিতরে prisma.product.update({ data: { status: "ARCHIVED" } }) চলে। পণ্যটি marketplace থেকে অদৃশ্য হয়, কিন্তু পুরোনো order, review ও trace সব অক্ষত থাকে।

কোথায় app/api/v1/products/[productId]/route.js

প্রশ্ন ৩২: Hard delete রাখলেন না কেন?

সহজ উত্তর
কারণ পুরোনো order ওই পণ্যটিকে নির্দেশ করে। মুছে ফেললে ক্রেতার order history ভেঙে যেত।

Technical
ডাটাবেসই এটি আটকে দেয়: OrderItem.productId → Product সম্পর্কে কোনো onDelete: Cascade নেই, তাই Prisma-র ডিফল্ট RESTRICT কার্যকর। order থাকলে PostgreSQL সারিটি মুছতেই দেবে না। তাছাড়া Review ও TraceEvent cascade-এ মুছে যেত — অর্থাৎ কৃষকের reputation-ও হঠাৎ বদলে যেত।

আরও প্রশ্ন করলে — “তাহলে পণ্য কি চিরকাল থাকবে?” → “হ্যাঁ, এবং সেটিই উদ্দেশ্য। এটি একটি ঐতিহাসিক রেকর্ড। তবে চাইলে কোনো order নেই এমন পণ্যের জন্য admin-only hard delete যোগ করা যেত।”

প্রশ্ন ৩৩: Archive করা পণ্য কি ফেরত আনা যায়?

সহজ উত্তর
হ্যাঁ। PATCH /products/{id} দিয়ে status: "active" করলেই আবার marketplace-এ ফিরে আসে — ছবি ও সব তথ্যসহ।

Technical
Restore-এর জন্য আলাদা endpoint নেই, কারণ এটি নিছক একটি status পরিবর্তন। Admin console-এ archived সারিতে “Restore” বোতাম আসে, আর কৃষক edit form-এর status drop-down থেকে করতে পারেন। দুটোতেই window.confirm দেখানো হয়।

প্রশ্ন ৩৪: Archive হলে wishlist বা cart-এ কী হয়?

সহজ উত্তর
Wishlist-এ সারিটি থেকে যায় (কিন্তু “অনুপলব্ধ” বলে চিহ্নিত হয় না — এটি একটি সীমাবদ্ধতা)। Cart-এ নতুন করে যোগ করা যায় না, আর আগে থেকে থাকলে checkout-এ আটকে যায়।

Technical
POST /cart/{userId}/items-এ শর্ত: if (!product || product.status !== "ACTIVE") throw 404।

প্রশ্ন ৩৫: OUT_OF_STOCK আর ARCHIVED — পার্থক্য কী?

সহজ উত্তর
OUT_OF_STOCK মানে “এখন নেই, পরে আসবে”; ARCHIVED মানে “আর বিক্রি করছি না”। দুটোই marketplace থেকে লুকানো থাকে।

Technical
কোডগতভাবে পার্থক্য শুধু অর্থে — filter একটিই: where.status = "ACTIVE"। ভবিষ্যতে OUT_OF_STOCK পণ্যকে “stock এলে জানাবো” বোতামসহ ধূসর করে দেখানো যেত।

G. Cart, Order ও Payment

প্রশ্ন ৩৬: Cart আর CartItem আলাদা টেবিল কেন? Order আর OrderItem-ও?

সহজ উত্তর
এটি database normalization। একটি cart-এ অনেক item থাকে — এটি one-to-many সম্পর্ক, তাই আলাদা টেবিল।

Technical
এক টেবিলে রাখলে একই ব্যবহারকারীর ঠিকানা, মোট দাম ইত্যাদি প্রতিটি সারিতে পুনরাবৃত্তি হতো (update anomaly)। আলাদা রাখায় Cart-এ ব্যবহারকারীর তথ্য একবার, আর CartItem-এ প্রতিটি পণ্য একবার। Order/OrderItem-ও একই যুক্তি।

প্রশ্ন ৩৭: OrderItem-এ পণ্যের নাম আবার কেন রাখলেন? Product থেকে join করলেই তো হয়!

সহজ উত্তর
কারণ কৃষক আগামীকাল নাম বা দাম বদলাতে পারেন — কিন্তু পুরোনো রসিদে সেদিনের নাম ও দামই থাকা উচিত।

Technical
এটিকে বলে ঐতিহাসিক নির্ভুলতার জন্য ইচ্ছাকৃত denormalization। nameSnapshot, unitPriceBdt ও lineTotalBdt checkout-এর মুহূর্তে কপি করা হয়। এটি একটি চমৎকার প্রশ্ন, কারণ এতে বোঝা যায় আপনি normalization-এর নিয়ম শুধু মুখস্থ করেননি — কখন ভাঙতে হয় তাও জানেন।

প্রশ্ন ৪৩: ভুয়া review কীভাবে ঠেকান?

প্রশ্ন ৪৮: Cascade আর Restrict কোথায় কোথায় ব্যবহার করেছেন?

Technical

DATABASE_URL pooled — অ্যাপ চলার জন্য; DIRECT_URL direct — শুধু migration-এর জন্য।

Technical
Serverless function ক্ষণস্থায়ী ও অসংখ্য; প্রত্যেকে নিজের সংযোগ খুললে PostgreSQL-এর সংযোগ-সীমা ফুরিয়ে যেত, তাই pooler। কিন্তু CREATE TABLE-এর মতো DDL-এর জন্য একটি স্থায়ী session লাগে, যা pooler দিতে পারে না — তাই migration সরাসরি সংযোগ ব্যবহার করে।

প্রশ্ন ৬০: আপনার প্রজেক্টের দুর্বলতা কী?

সহজ উত্তর
সবচেয়ে বড় তিনটি — প্রকৃত payment gateway নেই, Farmer Card verification একটি demo registry, আর rate limiting একক process-এর memory-তে।

বিস্তারিত
এছাড়া notification নেই, pagination নেই, profile সম্পাদনা নেই, integration test নেই। marketplace-এর search শুধু client-side। আমি এগুলো নথিভুক্ত করে রেখেছি এবং প্রতিটির সমাধানের পথও লিখেছি — কারণ কোনটা করা হয়নি তা জানাটাও প্রজেক্ট বোঝারই অংশ।

টিপ এই প্রশ্নে কখনো “কোনো দুর্বলতা নেই” বলবেন না। প্রস্তুত তালিকা থেকে ৩-৪টি বলুন, সাথে সমাধানের পথ।

প্রশ্ন ৬১: আবার শুরু করলে কী ভিন্নভাবে করতেন?

সহজ উত্তর
শুরু থেকেই PostgreSQL ব্যবহার করতাম, এবং route-level integration test লিখতাম।

বিস্তারিত
SQLite দিয়ে শুরু করে পরে PostgreSQL-এ যেতে গিয়ে case-sensitivity-র মতো সূক্ষ্ম পার্থক্য ধরা পড়েছিল (admin search ভেঙে যেত)। আর ownership/IDOR-এর জন্য স্বয়ংক্রিয় টেস্ট থাকলে প্রতিটি পরিবর্তনের পর নিশ্চিত থাকা যেত।

প্রশ্ন ৬২: “AI-Enabled” বলছেন — AI কোথায়?

সহজ উত্তর
সৎভাবে বললে — এই সংস্করণে কোনো প্রশিক্ষিত AI মডেল নেই। nutrition, scanner, health prediction — সবই সূত্র বা heuristic।

বিস্তারিত
শিরোনামের “AI-Enabled” বলতে বোঝানো হয়েছে যে স্থাপত্যটি AI যুক্ত করার জন্য প্রস্তুত — API contract নির্দিষ্ট, তাই /scanner/analyze-এর ভিতরের heuristic-টি একটি image classification মডেল দিয়ে বদলে দিলে বাইরের কিছুই বদলাবে না। আমি প্রতিটি demo module-এর UI-তে এটি স্পষ্ট করে লিখেও দিয়েছি।

টিপ এই প্রশ্নটি আসতে পারে এবং একটু কঠিন শোনায়। সরাসরি স্বীকার করে নিলে বোর্ড সন্তুষ্ট হন; লুকাতে গেলে বিপদ।

প্রশ্ন ৬৩: ১০,০০০ ব্যবহারকারী হলে কী হবে?

সহজ উত্তর
Vercel ও Neon নিজে থেকেই scale করে, কিন্তু তিনটি জায়গা আগে ঠিক করতে হবে — pagination, in-memory rate limiting, আর কিছু query-র index।

Technical
(১) কোনো তালিকায় pagination নেই, তাই ১০,০০০ পণ্য একবারে আসত। (২) Rate limit প্রতিটি instance-এ আলাদা — Redis লাগবে। (৩) Serverless-এ সংযোগ-সীমা: pooled DATABASE_URL ইতিমধ্যেই সেই সমস্যার সমাধান। index ইতিমধ্যেই প্রধান filter কলামগুলোতে আছে।

44“এটা কেন ব্যবহার করলেন?” — দ্রুত উত্তর তালিকা[[C44]]

ভাইভায় এই প্রশ্নগুলো দ্রুত একটার পর একটা আসে। প্রতিটির উত্তর এক বাক্যে মুখস্থ রাখুন।

প্রশ্নএক-বাক্যের উত্তর
Next.js কেন?Frontend ও backend একই প্রজেক্টে রাখা যায়, একবারে deploy হয়, আর Server Component-এর কারণে পেজ দ্রুত ও SEO-বান্ধব।
React কেন?Component-ভিত্তিক কাঠামোয় একই UI বারবার লেখা লাগে না — যেমন ProductImage সাতটি আলাদা পেজে ব্যবহৃত হয়।
Prisma কেন?একটি schema ফাইল থেকেই ডাটাবেস, migration ও type-safe query — আর parameterized query-র কারণে SQL injection-এর ঝুঁকি কমে।
PostgreSQL কেন?ডেটা সম্পূর্ণ relational, এবং foreign key, enum, cascade ও transaction — সবই আমার ব্যবসায়িক নিয়ম প্রয়োগে দরকার ছিল।
Neon কেন?Serverless PostgreSQL, connection pooling দেয়, free tier আছে, আর Vercel-এর সাথে সহজে যুক্ত হয়।
JWT কেন?Stateless — server-এ session রাখতে হয় না, যা serverless পরিবেশে অপরিহার্য।
bcrypt কেন?ইচ্ছাকৃতভাবে ধীর ও প্রতিটি পাসওয়ার্ডে আলাদা salt দেয়, তাই brute-force ও rainbow table কাজ করে না।
Zod কেন?ক্লায়েন্ট থেকে আসা প্রতিটি JSON-এর গঠন ও ধরন এক জায়গায় ঘোষণা করে যাচাই করা যায়; ব্যর্থ হলে 422।
Vercel কেন?Next.js-এর নির্মাতার প্ল্যাটফর্ম — git push করলেই deploy, preview URL, HTTPS ও Blob storage একসাথে।
Vercel Blob কেন?Serverless ফাইল সিস্টেম read-only ও ক্ষণস্থায়ী, তাই ছবি ডিস্কে রাখা যায় না।
REST কেন?সরল, সর্বজনীন, আর Next.js-এর route handler-এর সাথে স্বাভাবিকভাবে মেলে; ক্লায়েন্ট একটিই বলে GraphQL-এর দরকার পড়েনি।
Soft delete কেন?কারণ OrderItem → Product সম্পর্ক RESTRICT, আর পুরোনো order, review ও trace ইতিহাস অক্ষত রাখা প্ল্যাটফর্মের মূল প্রতিশ্রুতি।
Audit log কেন?Admin-এর হাতে অনেক ক্ষমতা; কে কখন কী করল তার প্রমাণ না থাকলে জবাবদিহি থাকে না।
Rate limiting কেন?পাসওয়ার্ড অনুমান, ভুয়া অ্যাকাউন্ট ও storage ভরে ফেলা ঠেকাতে।
Farmer verification কেন?নাহলে যে কেউ “কৃষক” সেজে বিক্রি করত, আর প্ল্যাটফর্মের মূল প্রতিশ্রুতিই মিথ্যা হয়ে যেত।
Reputation কেন?Verification বলে “সে কৃষক”; reputation বলে “সে ভালো কৃষক”।
Normalization কেন?একই তথ্য একাধিক জায়গায় থাকলে একটি বদলালে অন্যটি পুরোনো থেকে যেত (update anomaly)।
Order ও OrderItem আলাদা কেন?এক order-এ অনেক পণ্য — one-to-many সম্পর্ক; এক টেবিলে রাখলে ঠিকানা ও মোট দাম প্রতিটি সারিতে পুনরাবৃত্তি হতো।
Cart ও CartItem আলাদা কেন?একই যুক্তি; সাথে Cart.userId @unique নিশ্চিত করে প্রতি ব্যবহারকারীর একটিই ঝুড়ি।
Environment variable কেন?গোপন মান কোডে থাকলে git-এ চলে যেত; আর dev ও production-এ আলাদা মান দেওয়া যেত না।
Migration কেন?ডাটাবেসের প্রতিটি পরিবর্তন git-এ নথিভুক্ত থাকে, এবং production-এ একই ক্রমে নিরাপদে প্রয়োগ করা যায়।
Provider abstraction কেন?ভবিষ্যতে সরকারি API বা অন্য storage এলে শুধু একটি ফাইল বদলাতে হবে — route, schema বা frontend নয়।
Serializer কেন?Prisma model সরাসরি পাঠালে passwordHashও চলে যেত; serializer ঠিক করে দেয় কোন ফিল্ড বাইরে যাবে।
SDK প্যাকেজ কেন?API-র contract স্পষ্ট রাখে, আর ভবিষ্যতের মোবাইল অ্যাপ সরাসরি এটি ব্যবহার করতে পারবে।
