44“এটা কেন ব্যবহার করলেন?” — দ্রুত উত্তর তালিকা[[C44]]

ভাইভায় এই প্রশ্নগুলো দ্রুত একটার পর একটা আসে। প্রতিটির উত্তর এক বাক্যে মুখস্থ রাখুন।

প্রশ্নএক-বাক্যের উত্তর
Next.js কেন?Frontend ও backend একই প্রজেক্টে রাখা যায়, একবারে deploy হয়, আর Server Component-এর কারণে পেজ দ্রুত ও SEO-বান্ধব।
React কেন?Component-ভিত্তিক কাঠামোয় একই UI বারবার লেখা লাগে না — যেমন ProductImage সাতটি আলাদা পেজে ব্যবহৃত হয়।
Prisma কেন?একটি schema ফাইল থেকেই ডাটাবেস, migration ও type-safe query — আর parameterized query-র কারণে SQL injection-এর ঝুঁকি কমে।
PostgreSQL কেন?ডেটা সম্পূর্ণ relational, এবং foreign key, enum, cascade ও transaction — সবই আমার ব্যবসায়িক নিয়ম প্রয়োগে দরকার ছিল।
Neon কেন?Serverless PostgreSQL, connection pooling দেয়, free tier আছে, আর Vercel-এর সাথে সহজে যুক্ত হয়।
JWT কেন?Stateless — server-এ session রাখতে হয় না, যা serverless পরিবেশে অপরিহার্য।
bcrypt কেন?ইচ্ছাকৃতভাবে ধীর ও প্রতিটি পাসওয়ার্ডে আলাদা salt দেয়, তাই brute-force ও rainbow table কাজ করে না।
Zod কেন?ক্লায়েন্ট থেকে আসা প্রতিটি JSON-এর গঠন ও ধরন এক জায়গায় ঘোষণা করে যাচাই করা যায়; ব্যর্থ হলে 422।
Vercel কেন?Next.js-এর নির্মাতার প্ল্যাটফর্ম — git push করলেই deploy, preview URL, HTTPS ও Blob storage একসাথে।
Vercel Blob কেন?Serverless ফাইল সিস্টেম read-only ও ক্ষণস্থায়ী, তাই ছবি ডিস্কে রাখা যায় না।
REST কেন?সরল, সর্বজনীন, আর Next.js-এর route handler-এর সাথে স্বাভাবিকভাবে মেলে; ক্লায়েন্ট একটিই বলে GraphQL-এর দরকার পড়েনি।
Soft delete কেন?কারণ OrderItem → Product সম্পর্ক RESTRICT, আর পুরোনো order, review ও trace ইতিহাস অক্ষত রাখা প্ল্যাটফর্মের মূল প্রতিশ্রুতি।
Audit log কেন?Admin-এর হাতে অনেক ক্ষমতা; কে কখন কী করল তার প্রমাণ না থাকলে জবাবদিহি থাকে না।
Rate limiting কেন?পাসওয়ার্ড অনুমান, ভুয়া অ্যাকাউন্ট ও storage ভরে ফেলা ঠেকাতে।
Farmer verification কেন?নাহলে যে কেউ “কৃষক” সেজে বিক্রি করত, আর প্ল্যাটফর্মের মূল প্রতিশ্রুতিই মিথ্যা হয়ে যেত।
Reputation কেন?Verification বলে “সে কৃষক”; reputation বলে “সে ভালো কৃষক”।
Normalization কেন?একই তথ্য একাধিক জায়গায় থাকলে একটি বদলালে অন্যটি পুরোনো থেকে যেত (update anomaly)।
Order ও OrderItem আলাদা কেন?এক order-এ অনেক পণ্য — one-to-many সম্পর্ক; এক টেবিলে রাখলে ঠিকানা ও মোট দাম প্রতিটি সারিতে পুনরাবৃত্তি হতো।
Cart ও CartItem আলাদা কেন?একই যুক্তি; সাথে Cart.userId @unique নিশ্চিত করে প্রতি ব্যবহারকারীর একটিই ঝুড়ি।
Environment variable কেন?গোপন মান কোডে থাকলে git-এ চলে যেত; আর dev ও production-এ আলাদা মান দেওয়া যেত না।
Migration কেন?ডাটাবেসের প্রতিটি পরিবর্তন git-এ নথিভুক্ত থাকে, এবং production-এ একই ক্রমে নিরাপদে প্রয়োগ করা যায়।
Provider abstraction কেন?ভবিষ্যতে সরকারি API বা অন্য storage এলে শুধু একটি ফাইল বদলাতে হবে — route, schema বা frontend নয়।
Serializer কেন?Prisma model সরাসরি পাঠালে passwordHashও চলে যেত; serializer ঠিক করে দেয় কোন ফিল্ড বাইরে যাবে।
SDK প্যাকেজ কেন?API-র contract স্পষ্ট রাখে, আর ভবিষ্যতের মোবাইল অ্যাপ সরাসরি এটি ব্যবহার করতে পারবে।

45প্রজেক্ট ব্যাখ্যা — ৩০ সেকেন্ড থেকে ৫ মিনিট[[C45]]

45.1 ৩০ সেকেন্ডের সংস্করণ (মুখস্থ করুন)

“Fair Harvest একটি full-stack digital agricultural marketplace, যেখানে সরকারি Farmer Card দিয়ে verified কৃষকরা সরাসরি ক্রেতাদের কাছে পণ্য বিক্রি করতে পারেন। এর তিনটি মূল বৈশিষ্ট্য — কৃষক যাচাই, স্বয়ংক্রিয় reputation score, এবং প্রতিটি পণ্যের মাটি-থেকে-প্লেট traceability। আমি এটি বানিয়েছি Next.js, React, Prisma আর PostgreSQL দিয়ে, Vercel-এ deploy করা।”

45.2 ১ মিনিটের সংস্করণ

“Fair Harvest একটি full-stack digital agricultural marketplace। সমস্যাটি হলো — বাংলাদেশে কৃষক মধ্যস্বত্বভোগীর কারণে ন্যায্য দাম পান না, আর ক্রেতা জানেন না তার খাবার কোথা থেকে এসেছে।

আমার সমাধান তিনটি স্তম্ভের উপর দাঁড়িয়ে। এক — কৃষককে Government Farmer Card, NID ও নাম দিয়ে যাচাই করতে হয়; verified না হলে তিনি একটি পণ্যও তালিকাভুক্ত করতে পারেন না। দুই — প্রতিটি কৃষকের একটি reputation score আছে, যা verification, review rating ও delivery সম্পূর্ণতার হার থেকে স্বয়ংক্রিয়ভাবে গণনা হয়। তিন — প্রতিটি পণ্যের ছয় ধাপের trace timeline আছে, যা কৃষক নিজে লেখেন।

এর উপরে সাধারণ e-commerce অংশ — cart, checkout, order tracking আর review। তবে review দিতে হলে সেই পণ্যের একটি DELIVERED order থাকতেই হবে, যা server নিজে যাচাই করে।

প্রযুক্তিগতভাবে এটি Next.js 15 App Router-এ একটিই deployment, যা UI ও ৬৪টি REST endpoint দুটোই চালায়; Prisma ORM দিয়ে PostgreSQL, JWT authentication, আর Vercel-এ deploy করা।”

45.3 ২ মিনিটের সংস্করণ

উপরের ১ মিনিটের অংশটি বলুন, তারপর যোগ করুন —

“ভূমিকা তিনটি: CONSUMER কেনে ও review দেয়, FARMER পণ্য ও trace ব্যবস্থাপনা করে, ADMIN verification, moderation ও তত্ত্বাবধান করে। প্রতিটি রোলের আলাদা login পেজ আছে, আর প্রতিটি API route server-এ নিজে থেকে রোল ও মালিকানা যাচাই করে — UI-র guard শুধু সুবিধার জন্য।

ডাটাবেসে ১৫টি মডেল ও ১৩টি enum। একটি গুরুত্বপূর্ণ নকশা সিদ্ধান্ত — পণ্য কখনো ডাটাবেস থেকে মুছি না, শুধু ARCHIVED করি। কারণ OrderItem-এর foreign key RESTRICT, আর পুরোনো order, review ও trace ইতিহাস নষ্ট হওয়া চলবে না।

Checkout একটিমাত্র ডাটাবেস transaction-এ পাঁচটি কাজ করে — order ও item তৈরি, stock কমানো, payment রেকর্ড, reward point, আর cart খালি করা। তাই হয় সব হবে, নয়তো একটিও না।

সৎভাবে বলি — payment gateway ও সরকারি API এখনো demo। তবে দুটোর জন্যই আমি provider abstraction রেখেছি, তাই আসল সংযোগ এলে শুধু একটি ফাইল বদলালেই চলবে।”

45.4 ৫ মিনিটের কারিগরি সংস্করণ — ধাপে ধাপে

সময়বিষয়কী বলবেন
০:০০–০:৪৫সমস্যা ও সমাধানউপরের ১ মিনিটের অংশ
০:৪৫–১:৩০আর্কিটেকচার “একটি monolithic Next.js অ্যাপ — app/-এ UI, app/api/v1/**-এ ৬৪টি REST handler। স্তরগুলো: route handler → auth layer → business logic → Prisma → PostgreSQL। ছবি Vercel Blob-এ, ডাটাবেসে শুধু URL।”
১:৩০–২:১৫নিরাপত্তা “bcrypt cost 10 দিয়ে পাসওয়ার্ড, HS256 JWT ২ ঘণ্টার মেয়াদে। তিনটি helper — requireUser, requireRole, requireOwnerOrRole — প্রতিটি route-এ IDOR ঠেকায়। Zod দিয়ে সব input validation, পাঁচটি endpoint-এ rate limiting, NID ও card নম্বর সবসময় masked।”
২:১৫–৩:১৫মূল তিনটি ফিচার Verification-এর দুটি পথ (instant ও manual), reputation-এর সূত্র ও Rahim-এর ৯৭ স্কোরের হিসাব, এবং trace-এর ছয় ধাপ — যেখানে অসম্পূর্ণ ধাপে কোনো বানানো তারিখ বসানো হয় না।
৩:১৫–৪:০০ডাটাবেস “১৫টি মডেল। Cascade বনাম Restrict-এর পার্থক্য, nameSnapshot-এর মতো ইচ্ছাকৃত denormalization, Review-এর দুটি unique constraint, আর AuditLog-এ ইচ্ছাকৃতভাবে FK না রাখা।”
৪:০০–৪:৪৫Deployment ও পরীক্ষা “GitHub → Vercel; build কমান্ডেই prisma migrate deploy। Neon-এ pooled ও direct দুটি URL। ৩১টি unit test পাস, lint-এ ০ error। deploy করতে গিয়ে তিনটি প্রকৃত সমস্যা হয়েছিল, তিনটিরই মূল কারণ খুঁজে সমাধান করেছি।”
৪:৪৫–৫:০০সীমাবদ্ধতা “সৎভাবে — payment ও সরকারি API demo, rate limit in-memory, integration test নেই। প্রতিটির সমাধানের পথ আমি নথিভুক্ত করে রেখেছি।”

46সম্পূর্ণ সিস্টেম কীভাবে কাজ করে — একটি গল্প[[C46]]

এই অধ্যায়টি মুখস্থ করুন। বোর্ড যদি বলেন “পুরো সিস্টেমটা একবার বলুন” — এটিই বলবেন।

রহিম (কৃষক) → /auth/farmer-এ register
       ↓  User + খালি FarmerProfile তৈরি হয়, status = PENDING
       ↓  dashboard বলে: "Verification required" — Add product ফর্ম নেই
রহিম → /farmer/verify-এ Card BD-FARM-0001 + NID + নাম দেন
       ↓  GovFarmerCardRecord-এ lookup → তিনটিই মেলে → confidence 0.98
       ↓  verificationStatus = VERIFIED,  reputation পুনর্গণনা → 78 ("Reliable Farmer")
       ↓  dashboard unlock
রহিম → ছবি upload (3 MB সীমা, JPG/PNG/WebP) → products/<uuid>.jpg → URL
     → "Organic Spinach", 120 BDT/kg, 40 kg → POST /products (verification gate পাস)
     → Product তৈরি, status = ACTIVE
রহিম → trace event যোগ করেন: PLANTED → HARVESTED → LAB_TESTED → PACKAGED → SHIPPED → LISTED
       ↓
করিম (ক্রেতা) → /marketplace — শুধু ACTIVE পণ্য, trustScore অনুসারে সাজানো
       → product detail → "Verified farmer" badge, freshness window
       → /trace/<id> — ছয়টি ধাপ, GPS, এবং স্পষ্ট ঘোষণা: ledger_type = "database"
       → "Add" → login না থাকলে /auth/customer-এ পাঠায়
       → cart-এ যোগ (পণ্য ACTIVE কি না যাচাই হয়)
       → /checkout — ঠিকানা + Demo card
       ↓  একটি $transaction-এ:
          Order + OrderItem (nameSnapshot, দাম কপি) + OrderStatusEvent(PENDING)
          Product.quantityKg 40 → 38
          Payment (DEMO_CARD → PAID, ref = DEMO-xxxxxxxx)
          RewardsLedger +20
          CartItem মুছে ফেলা
       ↓  201 → /orders/<id>-এ redirect
রহিম/admin → status বদলান: CONFIRMED → SHIPPED → DELIVERED
       ↓  প্রতিবার একটি নতুন OrderStatusEvent যোগ হয় (পুরোনো কিছু মোছা হয় না)
       ↓  DELIVERED হওয়ায় রহিমের reputation পুনর্গণনা হয়
করিম → পণ্য পেজে এখন review ফর্ম দেখতে পান
       ↓  server যাচাই করে: DELIVERED OrderItem আছে? আগে review দিয়েছেন?
       ↓  ৫ তারা → Review তৈরি → reputation পুনর্গণনা → 97 ("Trusted Seller")
admin → /admin/dashboard — metrics
      → /admin/verification — অন্য pending কৃষকদের approve/reject (audit log-এ লেখা হয়)
      → /admin/reviews — আপত্তিকর review hide (reputation আবার বদলায়, audit লেখা হয়)
      → /admin/audit-log — সব সিদ্ধান্তের প্রমাণ
রহিম → পণ্যের মৌসুম শেষ → Archive (confirmation দেখায়)
       ↓  status = ARCHIVED — marketplace থেকে অদৃশ্য
       ↓  কিন্তু করিমের order, review ও trace সব অক্ষত (soft delete)
       ↓  audit log-এ product_archived লেখা হয়
এই গল্পটি কেন শক্তিশালী?

এতে প্রজেক্টের প্রতিটি মডিউল একবার করে আসে, ক্রমানুসারে — verification, product, image, trace, marketplace, cart, transaction, order status, review, reputation, admin, audit, soft delete। একটিও অতিরিক্ত দাবি নেই, আর কোথাও কিছু বাদ পড়েনি।

47.4 মুখস্থ রাখার সূত্র

Reputation = clamp( 0.35 × verification + 0.40 × review + 0.25 × delivery )

verification: VERIFIED 90 · PENDING 60 · REJECTED 30
review: (avg ÷ 5) × 100, না থাকলে 70 · delivery: (delivered ÷ মোট) × 100, না থাকলে 75
Badge: ≥90 Trusted Seller · ≥75 Reliable Farmer · ≥55 Growing Farmer · <55 New Farmer
