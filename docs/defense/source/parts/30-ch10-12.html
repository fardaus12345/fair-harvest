10Farmer Verification System[[C10]]

এটি এই প্রজেক্টের সবচেয়ে গুরুত্বপূর্ণ অধ্যায়

ভাইভা বোর্ড সবচেয়ে বেশি প্রশ্ন এখান থেকেই করবেন, কারণ এটিই Fair Harvest-কে সাধারণ e-commerce থেকে আলাদা করে। পুরো অধ্যায়টি ভালো করে পড়ুন।

10.1 কেন farmer verification দরকার?

যদি যে কেউ “আমি কৃষক” বলে register করেই পণ্য বিক্রি শুরু করতে পারে, তাহলে প্ল্যাটফর্মের মূল প্রতিশ্রুতি — “verified কৃষকের কাছ থেকে কিনছেন” — অর্থহীন হয়ে যায়। তাই Fair Harvest-এ একটি নিয়ম শক্তভাবে বসানো আছে:

verificationStatus === "VERIFIED" না হলে
POST /api/v1/products কখনোই সফল হবে না — 403।

10.2 verificationStatus-এর তিনটি অবস্থা

অবস্থাঅর্থকীভাবে এখানে আসেকৃষক কী করতে পারেন
PENDINGএখনো যাচাই হয়নি (ডিফল্ট) farmer হিসেবে register করলেই · অথবা card-এর তথ্য না মিললে login, dashboard দেখা, verification জমা দেওয়া। পণ্য যোগ করা যায় না, ছবি upload করা যায় না
VERIFIEDযাচাই সম্পন্ন card+NID+নাম মিললে তাৎক্ষণিক · অথবা admin approve করলে পণ্য যোগ/সম্পাদনা/archive, ছবি upload, trace event, order status বদল
REJECTEDadmin আবেদন নাকচ করেছেন শুধুই POST /admin/farmers/{id}/verification/reject দিয়ে PENDING-এর মতোই সীমিত; reputation-এর verification score ৩০-এ নেমে যায়

10.3 সম্পূর্ণ প্রবাহ (ধাপে ধাপে)

  1. Registration — /auth/farmer-এ “Create account”। POST /auth/register একই লেনদেনে User ও একটি খালি FarmerProfile তৈরি করে। ডিফল্ট verificationStatus = PENDING, reputationScore = 70, badge = "New Farmer"।
  2. Dashboard-এ সতর্কবার্তা — /farmer/dashboard-এ “Verification required — Product listing is locked until your Government Farmer Card is verified” লেখা একটি প্যানেল দেখায়, এবং “Add product” ফর্মটি একেবারেই render হয় না।
  3. ফর্ম পূরণ — /farmer/verify-তে তিনটি ঘর: Full name (as on card), Farmer Card number, NID number।
  4. API কল — POST /api/v1/farmers/{farmerId}/verify। প্রথমে rate limit (৮/মিনিট), তারপর requireOwnerOrRole(request, profile.userId, ["ADMIN"]) — অর্থাৎ একজন কৃষক অন্যজনের হয়ে আবেদন করতে পারেন না। তারপর Zod validation।
  5. Provider যাচাই — verifyFarmerCard() ডাকা হয় (বিস্তারিত অধ্যায় 11)।
  6. ডাটাবেস আপডেট — ফলাফল যাই হোক, জমা দেওয়া card ও NID সংরক্ষিত হয়: 
    verificationStatus: result.matched ? "VERIFIED" : "PENDING",
verificationMethod: result.matched
    ? (result.provider === "official" ? "OFFICIAL_API" : "DEMO_REGISTRY")
    : "MANUAL",
verifiedAt: result.matched ? new Date() : null
  7. Reputation পুনর্গণনা — recomputeFarmerReputation(farmerId) সাথে সাথে চলে, কারণ verification reputation-এর একটি উপাদান।
  8. Session সতেজ করা — frontend তারপর getMe() ডেকে localStorage-এর user object নতুন করে লেখে, যাতে dashboard সাথে সাথে unlock হয়।

10.4 Admin-এর manual review পথ

স্বয়ংক্রিয় যাচাই ব্যর্থ হলে profile PENDING থাকে এবং সে GET /api/v1/admin/farmers/verifications-এর তালিকায় চলে আসে (createdAt অনুসারে পুরোনো আগে — অর্থাৎ FIFO queue)।

সিদ্ধান্তEndpointডাটাবেসে কী লেখা হয়
ApprovePOST /api/v1/admin/farmers/{farmerId}/verification/approve VERIFIED · method = MANUAL · verifiedAt = now() · verifiedByAdminId = session.userId · audit action farmer_verification_approved
RejectPOST /api/v1/admin/farmers/{farmerId}/verification/reject REJECTED · method = MANUAL · verifiedAt = null · verifiedByAdminId সংরক্ষিত · audit action farmer_verification_rejected

verifiedByAdminId একটি self-relation — User মডেলে verifiedFarmers FarmerProfile[] @relation("VerifiedByAdmin") হিসেবে ফিরে আসে। অর্থাৎ ডাটাবেসেই লেখা থাকে কোন admin কোন কৃষককে verify করেছেন।

11Government Farmer Card System[[C11]]

সবার আগে সবচেয়ে জরুরি সত্যটি

এই প্রজেক্টে বাংলাদেশ সরকারের কোনো প্রকৃত API-র সাথে সংযোগ নেই। যাচাই হয় প্রজেক্টের নিজের ডাটাবেসের GovFarmerCardRecord টেবিলের বিপরীতে, যেখানে seed ফাইল দিয়ে ৮টি নমুনা কার্ড ঢোকানো হয়েছে। এটি একটি simulated / demo registry। বোর্ড এই প্রশ্নটি করবেনই — সরাসরি স্বীকার করে নিলে সেটি দুর্বলতা নয়, সততা হিসেবে গণ্য হয়।

11.1 Farmer Card কী এবং কেন?

বাংলাদেশে কৃষকদের জন্য সরকারি “কৃষি উপকরণ সহায়তা কার্ড” বা Farmer Card থাকে, যেখানে কৃষকের নাম, NID, জেলা ইত্যাদি লেখা থাকে। Fair Harvest এই ধারণাটিকে ডিজিটাল পরিচয় যাচাইয়ের ভিত্তি হিসেবে ব্যবহার করে — কারণ এটি এমন একটি নথি যা শুধু প্রকৃত কৃষকেরই থাকে।

11.2 GovFarmerCardRecord মডেল

model GovFarmerCardRecord {
  id         String        @id @default(cuid())
  cardNumber String        @unique      // BD-FARM-0001
  nidNumber  String
  fullName   String
  district   String
  issueDate  DateTime
  status     GovCardStatus @default(ACTIVE)   // ACTIVE | REVOKED
  cropTypes  String?
}

খেয়াল করুন: এই টেবিলের সাথে FarmerProfile-এর কোনো foreign key নেই। এটি ইচ্ছাকৃত — বাস্তব জীবনে সরকারি রেজিস্ট্রি একটি বাইরের ব্যবস্থা, আমাদের ডাটাবেসের অংশ নয়। তাই এখানেও এটিকে শুধু lookup table হিসেবে রাখা হয়েছে, যাতে ভবিষ্যতে এটিকে সত্যিকারের API দিয়ে প্রতিস্থাপন করা যায়।

12Farmer Reputation / Trust Score[[C12]]

12.1 কেন reputation দরকার?

Verification শুধু বলে “এই লোক সত্যিই কৃষক”। কিন্তু সে ভালো কৃষক কি না — সময়মতো পণ্য পৌঁছায় কি না, ক্রেতারা সন্তুষ্ট কি না — সেটি বলে না। reputation score সেই ফাঁকটি পূরণ করে।

12.2 সূত্র (আসল কোড থেকে)

// lib/server/reputation.js
const verificationScore =
  verificationStatus === "VERIFIED" ? 90 : verificationStatus === "PENDING" ? 60 : 30;

const reviewScore   = reviewCount    > 0 ? clamp((avgRating / 5) * 100)          : 70;
const deliveryScore = totalOrderItems > 0 ? clamp((deliveredCount / totalOrderItems) * 100) : 75;

const overallScore = clamp(
    verificationScore * 0.35
  + reviewScore       * 0.40
  + deliveryScore     * 0.25
);

Score = clamp( 0.35 × Sverification + 0.40 × Sreview + 0.25 × Sdelivery )

উপাদানওজনকীভাবে গণনা হয়ইতিহাস না থাকলে
Verification score35%VERIFIED → 90 · PENDING → 60 · REJECTED → 30প্রযোজ্য নয় (সবসময় একটি status থাকে)
Review score40%(গড় rating ÷ 5) × 100 — শুধু PUBLISHED review গোনা হয়70 (নিরপেক্ষ ভিত্তি, 0 নয়)
Delivery score25%(DELIVERED order item ÷ মোট order item) × 10075 (নিরপেক্ষ ভিত্তি)
কেন ইতিহাস না থাকলে 0 নয়, 70/75?

কারণ একজন নতুন verified কৃষককে শাস্তি দেওয়া অন্যায় হতো। তার তো এখনো কোনো review বা order-ই নেই। কোডের কমেন্টেই লেখা আছে: “so a brand-new verified farmer isn't penalized for having no history yet.” এটি একটি সচেতন ডিজাইন সিদ্ধান্ত — ভাইভায় এটি বললে ভালো প্রভাব পড়বে।

12.5 কখন পুনরায় গণনা হয়?

recomputeFarmerReputation() চারটি ঘটনার পরে ডাকা হয় এবং ফলাফল FarmerProfile-এ লিখে রাখা হয়:

ঘটনাফাইল
নতুন review জমা পড়লapp/api/v1/reviews/route.js
Farmer Card verification জমা পড়লapp/api/v1/farmers/[farmerId]/verify/route.js
Order DELIVERED বা CANCELLED হলোapp/api/v1/orders/[id]/status/route.js
Admin কোনো review hide/republish করলapp/api/v1/admin/reviews/[reviewId]/route.js

আর GET /api/v1/farmers/{id}/score ডাকলে getFarmerReputationBreakdown() ব্যবহার হয় — এটি কিছু লেখে না, শুধু বর্তমান মান হিসাব করে ফেরত দেয়। GET request-এ ডাটাবেস লেখা উচিত নয় বলেই এই দুটি আলাদা রাখা হয়েছে।

ফিল্ডকার উপরকীভাবে নির্ধারিত হয়
FarmerProfile.reputationScoreকৃষকের উপর স্বয়ংক্রিয়ভাবে গণনা করা — উপরের সূত্র অনুযায়ী সত্যিকারের
Product.trustScoreপণ্যের উপর ডিফল্ট 80; seed ডেটায় হাতে বসানো (spinach 91, tomato 86)। কোনো API এটি স্বয়ংক্রিয়ভাবে পরিবর্তন করে না। আংশিক — মূলত স্থির মান

বোর্ড যদি marketplace কার্ডের “91%” দেখে জিজ্ঞেস করেন “এটা কোথা থেকে এলো?” — সৎ উত্তর: “ওটি Product.trustScore, যা এখনো স্বয়ংক্রিয় নয়; কৃষকের reputation-ই কেবল সত্যিকারের গণনা করা মান।”
