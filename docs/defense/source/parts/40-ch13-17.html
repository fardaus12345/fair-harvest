13.2 “কৃষক একটি পণ্য যোগ করলে কী কী ঘটে?” (ধাপে ধাপে)

  1. Dashboard-এ “Add product” ফর্ম পূরণ: নাম, category, দাম, stock, এবং ঐচ্ছিক ছবি।
  2. ছবি দিলে আগে সেটি upload হয় (অধ্যায় 15) এবং draft.image_url-এ URL বসে।
  3. Submit → createProduct() → POST /api/v1/products, সাথে Authorization: Bearer header।
  4. requireUser(request) — login না থাকলে 401।
  5. Zod createProductSchema: price_bdt ও quantity_kg অবশ্যই ধনাত্মক, category অবশ্যই চারটির একটি, image_url সর্বোচ্চ ২০৪৮ অক্ষর। ভুল হলে 422।
  6. farmerProfile.findUnique({ id: farmer_id }) — না পেলে 404।
  7. মালিকানা যাচাই: farmer.userId !== session.userId এবং role ADMIN নয় → 403। অর্থাৎ একজন কৃষক অন্যজনের নামে পণ্য দিতে পারেন না।
  8. Verification যাচাই: farmer.verificationStatus !== "VERIFIED" → 403 "Only verified farmers can list products"।
  9. prisma.product.create() — status ডিফল্ট ACTIVE (lowercase ইনপুটকে .toUpperCase() করে enum-এ বসানো হয়)।
  10. 201 + toPublicProduct() দিয়ে সাজানো object। Dashboard তালিকা রিফ্রেশ করে।

13.3 পণ্য সম্পাদনা (Edit)

PATCH /api/v1/products/{productId} — assertOwnerOrAdmin() দিয়ে মালিকানা যাচাই। সব ফিল্ড ঐচ্ছিক; শুধু যেটি পাঠানো হয় সেটিই বদলায়:

...(data.price_bdt !== undefined ? { priceBdt: data.price_bdt } : {}),
...(data.status    !== undefined ? { status: data.status.toUpperCase() } : {})

ছবি বদলালে পুরোনো ফাইলটি মুছে ফেলা হয়, যাতে storage-এ অনাথ (orphan) ফাইল জমে না থাকে:

if (data.image_url !== undefined && product.imageUrl && product.imageUrl !== updated.imageUrl) {
  const staleKey = storageKeyFromUrl(product.imageUrl);
  if (staleKey) await deleteObject(staleKey).catch(() => null);   // best-effort
}

লক্ষণীয় — .catch(() => null)। ছবি মুছতে ব্যর্থ হলেও পণ্য আপডেট ব্যর্থ হয় না, কারণ মূল কাজটি হলো তথ্য হালনাগাদ করা।

13.5 Admin search — একটি বাস্তব বাগ যা ধরা পড়েছিল

PostgreSQL-এ যাওয়ার পর যা শিখতে হলো

SQLite-এ ASCII লেখার তুলনা ডিফল্টভাবে case-insensitive, কিন্তু PostgreSQL-এ LIKE case-sensitive। ফলে “spinach” লিখে খুঁজলে “Organic Spinach” আর পাওয়া যেত না। সমাধান — Prisma-র mode: "insensitive":

where.OR = [
  { name:        { contains: search, mode: "insensitive" } },
  { description: { contains: search, mode: "insensitive" } },
  { farmer: { user: { name: { contains: search, mode: "insensitive" } } } }
];

এটি ভাইভায় বলার মতো একটি ভালো উদাহরণ — “ডাটাবেস বদলালে শুধু connection string বদলালেই হয় না, আচরণও যাচাই করতে হয়।”

14Product Status, Archive ও Soft Delete[[C14]]

14.1 তিনটি status

Statusঅর্থকে বসাতে পারেMarketplace-এক্রেতা কিনতে পারে?
ACTIVEবিক্রির জন্য উন্মুক্ত (ডিফল্ট) মালিক কৃষক বা adminদেখা যায়হ্যাঁ
OUT_OF_STOCKসাময়িকভাবে শেষ মালিক কৃষক বা admin (PATCH status)দেখা যায় না না — cart-এ যোগ করলে 404 "Product is not available"
ARCHIVEDতালিকা থেকে সরানো, কিন্তু মুছে ফেলা হয়নি মালিক কৃষক বা admin (DELETE)দেখা যায় নানা
গুরুত্বপূর্ণ কারিগরি বিবরণ

Marketplace-এর filter-টি বাস্তবে এভাবে কাজ করে:

// app/api/v1/products/route.js
if (!farmerId) where.status = "ACTIVE";

অর্থাৎ — farmer_id ছাড়া query (মানে public marketplace) শুধু ACTIVE দেখায়। কিন্তু ?farmer_id=… দিলে সব status ফেরত আসে, কারণ কৃষককে নিজের archived পণ্যও দেখতে হবে।

14.2 Hard delete কেন নেই?

এটি ভাইভার একটি প্রিয় প্রশ্ন। উত্তরটি ডাটাবেসের গঠনেই লেখা আছে:

model OrderItem {
  productId  String
  product    Product @relation(fields: [productId], references: [id])
  // ↑ কোনো onDelete: Cascade নেই → Prisma-র ডিফল্ট = RESTRICT
}

মানে — যে পণ্যের বিপরীতে একটিও order আছে, সেটিকে ডাটাবেস মুছতেই দেবে না। আর মুছতে পারলেও ক্ষতি হতো:

যদি hard delete করা হতোকী ভেঙে যেত
পুরোনো orderক্রেতার order history-তে পণ্যের নাম থাকত না; হিসাব মেলানো যেত না
ReviewReview.productId → Product cascade, তাই review-ও মুছে যেত এবং কৃষকের reputation হঠাৎ বদলে যেত
TraceEventপণ্যের পুরো ইতিহাস হারিয়ে যেত — অথচ traceability এই প্রজেক্টের মূল প্রতিশ্রুতি
Farmer earningsবিক্রির হিসাব পাল্টে যেত

14.3 Archive করলে ঠিক কী হয়?

DELETE /api/v1/products/{productId} — নাম DELETE হলেও এটি সারিটি মুছে না, শুধু status বদলায়:

export async function DELETE(request, { params }) {
  const session = requireUser(request);
  enforceRateLimit(request, "product-archive", { max: 20, windowMs: 60_000 });
  const product = await loadProduct(productId);
  assertOwnerOrAdmin(session, product);

  const archived = await prisma.product.update({
    where: { id: productId }, data: { status: "ARCHIVED" }, …
  });

  await recordAudit({ actorId: session.userId, actorRole: session.role,
    action: "product_archived", targetType: "Product", targetId: productId,
    metadata: { previousStatus: product.status, farmerId: product.farmerId } });

  return ok({ product: toPublicProduct(archived) }, { message: "Product archived" });
}
কীArchive-এর পরে অবস্থা
ডাটাবেস সারিঅক্ষত থাকে, শুধু status = ARCHIVED
Marketplaceআর দেখা যায় না
পুরোনো orderসম্পূর্ণ অক্ষত — nameSnapshot ও দামও OrderItem-এ আলাদা করে রাখা
Reviewঅক্ষত, reputation-এ গোনা চলতেই থাকে
TraceEventঅক্ষত; /trace/<id> পেজ কাজ করে
Wishlistসারিটি থেকে যায়, পণ্যটি wishlist পেজে দেখা যায় ছোট সীমাবদ্ধতা — archived বলে আলাদা চিহ্ন দেখানো হয় না
Cartআগে থেকে cart-এ থাকলে সারিটি থাকে, কিন্তু checkout-এ stock যাচাইয়ে আটকে যায় আংশিক
ছবিমুছে ফেলা হয় না — restore করলে ছবিও ফিরে আসে
Audit logএকটি product_archived এন্ট্রি লেখা হয়

14.4 Restore

Restore-এর জন্য আলাদা কোনো endpoint নেই; এটি সাধারণ একটি update: PATCH /api/v1/products/{id} with { status: "active" }। Admin console-এ archived পণ্যের সারিতে “Restore” বোতাম আসে; কৃষক নিজের edit form-এর Status drop-down থেকে আবার active বেছে নিতে পারেন।

14.5 ভুল ক্লিক ঠেকানো — confirmation

Archive ও Restore — দুটোতেই ব্রাউজারের confirmation দেখানো হয়, যাতে একটি অসতর্ক ক্লিকে listing বাজার থেকে সরে না যায়:

const confirmed = window.confirm(
  `Archive "${product.name}"?\n\nIt will no longer appear in the marketplace, `
  + "but it can be restored later.");
if (!confirmed) return;

এটি FarmerProductRow.js ও app/admin/products/page.js — দুই জায়গাতেই আছে।

Soft Delete (নরম মুছে ফেলা) — এক বাক্যে

“Soft delete মানে ডেটা মুছে না ফেলে শুধু নিষ্ক্রিয় করে রাখা। Fair Harvest-এ পণ্য কখনো ডাটাবেস থেকে মুছি না, শুধু ARCHIVED করি — কারণ OrderItem-এর foreign key RESTRICT, আর পুরোনো order, review ও trace ইতিহাস ঠিক রাখা প্ল্যাটফর্মের মূল প্রতিশ্রুতি।”

15.3 দুটি storage provider

STORAGE_PROVIDERProvider ফাইলকোথায় রাখেযে URL ফেরত দেয়
local (ডিফল্ট)localDiskProvider.js UPLOAD_DIR (ডিফল্ট ./storage/uploads) আপেক্ষিক: /api/v1/uploads/<key>

Production-এ অবশ্যই object লাগবে — কেন?

Vercel-এর serverless function-এর ফাইল সিস্টেম /tmp ছাড়া read-only, আর প্রতিটি invocation-এর পর সেটি মুছে যায়। তাই local provider production-এ চললে ENOENT: no such file or directory, mkdir '/var/task/fair-harvest-web/storage' ত্রুটি দেয় — এই প্রজেক্টে বাস্তবে এই সমস্যাটি ঘটেছিল এবং STORAGE_PROVIDER=object সেট করে সমাধান হয়েছে।

15.4 ছবি মোছা — orphan ঠেকানো

storageKeyFromUrl() একটি সংরক্ষিত URL থেকে আবার key বের করে আনে। দুটি রূপই এটি বোঝে:

// (১) local: "/api/v1/uploads/products/abc.jpg"  →  "products/abc.jpg"
// (২) object: "https://xyz.public.blob.vercel-storage.com/products/abc.jpg"
//              → BLOB_PUBLIC_BASE_URL বাদ দিয়ে → "products/abc.jpg"

দ্বিতীয় শাখাটি না থাকলে Vercel Blob-এ প্রতিস্থাপিত প্রতিটি ছবি চিরকাল bucket-এ পড়ে থাকত, যার সাথে কোনো পণ্যের সংযোগ নেই — অর্থাৎ ধীরে ধীরে জমতে থাকা আবর্জনা।

15.5 ডাটাবেসে ছবি রাখা হয় না — কেন?

Product.imageUrl শুধু একটি string। ছবির bytes কখনো PostgreSQL-এ যায় না। কারণ — (ক) ডাটাবেস বড় হয়ে ব্যাকআপ ও query ধীর হয়ে যেত, (খ) CDN থেকে ছবি পরিবেশন করা অনেক দ্রুত ও সস্তা, (গ) ডাটাবেস সারিটি ছোট থাকলে join ও index দ্রুত কাজ করে।

15.6 ছবি না থাকলে?

components/products/ProductImage.js একটি gradient টাইল দেখায় যেখানে category অনুযায়ী লেখা থাকে (Fresh / Fruit / Grain / Herb), এবং screen-reader-এর জন্য aria-label-এ “(no photo)” যোগ করে। এতে কোনো ভাঙা ছবির আইকন দেখা যায় না।

17Traceability — মাটি থেকে প্লেট[[C17]]

17.1 ধারণাটি কী?

প্রতিটি পণ্যের জীবনে ছয়টি ধাপ থাকে। কৃষক প্রতিটি ধাপ ঘটার সাথে সাথে একটি TraceEvent সারি যোগ করেন, আর ক্রেতা /trace/<productId> পেজে সেই timeline দেখতে পান।

#TraceStageবাংলাসাধারণত কী বোঝায়
1PLANTEDরোপণবীজ বোনা হলো
2HARVESTEDফসল তোলাফসল কাটা হলো
3LAB_TESTEDল্যাব পরীক্ষাকীটনাশকের অবশিষ্টাংশ পরীক্ষা
4PACKAGEDপ্যাকেজিংবাক্সে ভরা হলো
5SHIPPEDপরিবহনবিতরণ কেন্দ্রে পাঠানো
6LISTEDতালিকাভুক্তFair Harvest-এ বিক্রির জন্য এলো

17.2 কে event যোগ করতে পারে?

POST /api/v1/trace/{productId} — requireUser, তারপর:

if (session.role !== "ADMIN" && session.userId !== product.farmer.userId) {
  throw new ApiError("You do not have permission to update this product's trace", 403);
}

Zod দিয়ে stage (ছয়টির একটি), ঐচ্ছিক note (সর্বোচ্চ ৫০০ অক্ষর) এবং ঐচ্ছিক GPS (lat -90…90, lng -180…180) যাচাই হয়।

17.3 যে ধাপ এখনো হয়নি, সেটি কী দেখায়?

toPublicTrace() সবসময় ছয়টি ধাপই ফেরত দেয়, কিন্তু যেটির কোনো event নেই সেটির completed: false ও timestamp: null। UI-তে সেটি ধূসর “Pending” হিসেবে দেখায়।

এটি একটি সৎ ডিজাইন

অনেক প্রজেক্টে খালি ধাপগুলোতে বানানো তারিখ বসিয়ে দেওয়া হয়, যাতে দেখতে ভালো লাগে। এখানে ইচ্ছাকৃতভাবে তা করা হয়নি — কোডের কমেন্টেই লেখা: “no fabricated timestamps.”

17.4 Blockchain আছে কি? — না

API response-এ দুটি ফিল্ড ইচ্ছাকৃতভাবে রাখা হয়েছে যাতে কেউ ভুল না বোঝে:

ledger_type: "database",
verification_note: "Traceability data is stored in the Fair Harvest database and
                    entered by the farmer. No blockchain or third-party ledger is used."

কোডের কমেন্টেও লেখা আছে — একটি verified_on_chain boolean রাখা হয়নি, কারণ সেটি একটি সাধারণ ডাটাবেস সারিকে “on-chain সত্য” বলে ভুলভাবে উপস্থাপন করত।

হোমপেজে একটি অসঙ্গতি — নিজে থেকেই স্বীকার করুন

হোমপেজের TrustCard-এ একটি স্থির “On-chain” লেখা chip আছে (app/page.js-এর <span className="chainChip">On-chain</span>)। এটি নিছক ডিজাইনের লেখা; এর পিছনে কোনো blockchain নেই এবং trace পেজ স্পষ্টভাবে উল্টো কথা বলে। বোর্ড ধরলে সরাসরি বলুন এটি একটি অবশিষ্ট UI লেবেল যা সরানো উচিত।

17.5 QR কোড

Response-এ qr_code: "qr_<productId>" নামে একটি স্ট্রিং আসে এবং trace পেজে সেটি লেখা হিসেবে দেখানো হয়। কোনো প্রকৃত QR ছবি তৈরি বা স্ক্যান করা হয় না — এটি একটি পরিচয়সূচক স্ট্রিং মাত্র।
