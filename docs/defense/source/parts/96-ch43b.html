F. পণ্য, Archive ও Soft Delete

প্রশ্ন ৩১: পণ্য delete করলে কী হয়?

সহজ উত্তর
ডাটাবেস থেকে মুছে যায় না — শুধু status হয়ে যায় ARCHIVED। একে বলে soft delete।

Technical
Endpoint-এর নাম DELETE হলেও ভিতরে prisma.product.update({ data: { status: "ARCHIVED" } }) চলে। পণ্যটি marketplace থেকে অদৃশ্য হয়, কিন্তু পুরোনো order, review ও trace সব অক্ষত থাকে।

কোথায় app/api/v1/products/[productId]/route.js

প্রশ্ন ৩২: Hard delete রাখলেন না কেন?

সহজ উত্তর
কারণ পুরোনো order ওই পণ্যটিকে নির্দেশ করে। মুছে ফেললে ক্রেতার order history ভেঙে যেত।

Technical
ডাটাবেসই এটি আটকে দেয়: OrderItem.productId → Product সম্পর্কে কোনো onDelete: Cascade নেই, তাই Prisma-র ডিফল্ট RESTRICT কার্যকর। order থাকলে PostgreSQL সারিটি মুছতেই দেবে না। তাছাড়া Review ও TraceEvent cascade-এ মুছে যেত — অর্থাৎ কৃষকের reputation-ও হঠাৎ বদলে যেত।

আরও প্রশ্ন করলে — “তাহলে পণ্য কি চিরকাল থাকবে?” → “হ্যাঁ, এবং সেটিই উদ্দেশ্য। এটি একটি ঐতিহাসিক রেকর্ড। তবে চাইলে কোনো order নেই এমন পণ্যের জন্য admin-only hard delete যোগ করা যেত।”

প্রশ্ন ৩৩: Archive করা পণ্য কি ফেরত আনা যায়?

সহজ উত্তর
হ্যাঁ। PATCH /products/{id} দিয়ে status: "active" করলেই আবার marketplace-এ ফিরে আসে — ছবি ও সব তথ্যসহ।

Technical
Restore-এর জন্য আলাদা endpoint নেই, কারণ এটি নিছক একটি status পরিবর্তন। Admin console-এ archived সারিতে “Restore” বোতাম আসে, আর কৃষক edit form-এর status drop-down থেকে করতে পারেন। দুটোতেই window.confirm দেখানো হয়।

প্রশ্ন ৩৪: Archive হলে wishlist বা cart-এ কী হয়?

সহজ উত্তর
Wishlist-এ সারিটি থেকে যায় (কিন্তু “অনুপলব্ধ” বলে চিহ্নিত হয় না — এটি একটি সীমাবদ্ধতা)। Cart-এ নতুন করে যোগ করা যায় না, আর আগে থেকে থাকলে checkout-এ আটকে যায়।

Technical
POST /cart/{userId}/items-এ শর্ত: if (!product || product.status !== "ACTIVE") throw 404।

প্রশ্ন ৩৫: OUT_OF_STOCK আর ARCHIVED — পার্থক্য কী?

সহজ উত্তর
OUT_OF_STOCK মানে “এখন নেই, পরে আসবে”; ARCHIVED মানে “আর বিক্রি করছি না”। দুটোই marketplace থেকে লুকানো থাকে।

Technical
কোডগতভাবে পার্থক্য শুধু অর্থে — filter একটিই: where.status = "ACTIVE"। ভবিষ্যতে OUT_OF_STOCK পণ্যকে “stock এলে জানাবো” বোতামসহ ধূসর করে দেখানো যেত।

G. Cart, Order ও Payment

প্রশ্ন ৩৬: Cart আর CartItem আলাদা টেবিল কেন? Order আর OrderItem-ও?

সহজ উত্তর
এটি database normalization। একটি cart-এ অনেক item থাকে — এটি one-to-many সম্পর্ক, তাই আলাদা টেবিল।

Technical
এক টেবিলে রাখলে একই ব্যবহারকারীর ঠিকানা, মোট দাম ইত্যাদি প্রতিটি সারিতে পুনরাবৃত্তি হতো (update anomaly)। আলাদা রাখায় Cart-এ ব্যবহারকারীর তথ্য একবার, আর CartItem-এ প্রতিটি পণ্য একবার। Order/OrderItem-ও একই যুক্তি।

প্রশ্ন ৩৭: OrderItem-এ পণ্যের নাম আবার কেন রাখলেন? Product থেকে join করলেই তো হয়!

সহজ উত্তর
কারণ কৃষক আগামীকাল নাম বা দাম বদলাতে পারেন — কিন্তু পুরোনো রসিদে সেদিনের নাম ও দামই থাকা উচিত।

Technical
এটিকে বলে ঐতিহাসিক নির্ভুলতার জন্য ইচ্ছাকৃত denormalization। nameSnapshot, unitPriceBdt ও lineTotalBdt checkout-এর মুহূর্তে কপি করা হয়। এটি একটি চমৎকার প্রশ্ন, কারণ এতে বোঝা যায় আপনি normalization-এর নিয়ম শুধু মুখস্থ করেননি — কখন ভাঙতে হয় তাও জানেন।

প্রশ্ন ৩৮: Checkout-এর সময় ঠিক কী কী ঘটে?

সহজ উত্তর
একটিমাত্র ডাটাবেস transaction-এ পাঁচটি কাজ — Order ও OrderItem তৈরি, stock কমানো, Payment তৈরি, ২০ reward point দেওয়া, আর cart খালি করা।

Technical
prisma.$transaction(async (tx) => { … })। আগে যাচাই হয় — cart খালি কি না (400) এবং প্রতিটি item-এর জন্য product.quantityKg < item.quantityKg (409)।

কোথায় app/api/v1/orders/[id]/checkout/route.js

প্রশ্ন ৩৯: Transaction কেন দরকার?

সহজ উত্তর
যাতে হয় সব কাজ হয়, নয়তো একটিও না হয়।

বিস্তারিত
ধরুন order তৈরি হলো কিন্তু stock কমানোর আগে server বন্ধ হয়ে গেল — তাহলে এমন একটি order থাকত যার জন্য কোনো stock কাটা হয়নি। Transaction ব্যর্থ হলে ডাটাবেস আগের অবস্থায় ফিরে যায় (rollback)। এটি ACID-এর A — Atomicity।

প্রশ্ন ৪০: Payment কি আসল?

সহজ উত্তর
না, সম্পূর্ণ demo। কোনো payment gateway নেই, কোনো আসল টাকা লেনদেন হয় না।

বিস্তারিত
দুটি পদ্ধতি আছে: DEMO_CARD (কোড সরাসরি PAID লিখে দেয়, কার্ড নম্বর চাওয়াই হয় না) আর COD (PENDING থাকে)। enum-এর নাম, demoTransactionRef ফিল্ড আর UI-র “Payment (demo)” লেখা — সব জায়গায় এটি স্বীকার করা আছে।

আরও প্রশ্ন করলে — “আসল payment যোগ করতে কত কাজ?” → “Payment মডেল ইতিমধ্যেই আছে। bKash বা SSLCommerz-এর sandbox যোগ করে তাদের webhook দিয়ে PaymentStatus হালনাগাদ করলেই হবে — checkout-এর বাকি যুক্তি অপরিবর্তিত থাকবে।”

প্রশ্ন ৪১: Order-এর status কে বদলাতে পারে?

সহজ উত্তর
Admin যেকোনো order, আর কৃষক শুধু সেই order যেখানে তার নিজের পণ্য আছে। ক্রেতা পারেন না।

Technical
order.items.some(item => item.farmerId === farmerProfile.id) — না হলে 403। প্রতিটি পরিবর্তনে একটি OrderStatusEvent যোগ হয়, আর DELIVERED বা CANCELLED হলে ওই order-এর প্রতিটি কৃষকের reputation নতুন করে গণনা হয়।

সীমাবদ্ধতা স্বীকার করুন কোনো state machine নেই — PENDING থেকে সরাসরি DELIVERED-এ যাওয়া যায়।

প্রশ্ন ৪২: একই order-এ দুই কৃষকের পণ্য থাকলে?

সহজ উত্তর
দুজনেই শুধু নিজের item দেখেন। কেউ অন্যের অংশ বা ক্রেতার পুরো বিল দেখতে পান না।

Technical
GET /farmer/orders Order নয়, OrderItem-এর উপর query করে, এবং farmerId session থেকে নেওয়া। এটি একটি সচেতন privacy সিদ্ধান্ত।

H. Review

প্রশ্ন ৪৩: ভুয়া review কীভাবে ঠেকান?

সহজ উত্তর
তিন স্তরে — UI-তে form লুকানো, server-এ DELIVERED order যাচাই, আর ডাটাবেসে দুটি unique constraint।

Technical
Server নিজে prisma.orderItem.findFirst({ where: { productId, order: { userId: customerId, status: "DELIVERED" } } }) চালায় — ক্লায়েন্টের দাবি বিশ্বাস করে না। তারপর ডাটাবেসে orderItemId @unique (এক ক্রয় = এক review) এবং @@unique([customerId, productId]) (এক ক্রেতা এক পণ্যে একবার) — কোড ভুল করলেও ডাটাবেস আটকে দেবে।

প্রশ্ন ৪৪: দুটি unique constraint কেন? একটিতে হতো না?

সহজ উত্তর
দুটি আলাদা আক্রমণ ঠেকায়। প্রথমটি একই ক্রয়ে দুইবার review; দ্বিতীয়টি একই পণ্য পাঁচবার কিনে পাঁচটি ৫-তারা দেওয়া (review farming)।

প্রশ্ন ৪৫: Admin কি খারাপ review মুছে দিতে পারেন?

সহজ উত্তর
মুছতে পারেন না, শুধু HIDDEN করতে পারেন। সারিটি ডাটাবেসে থেকে যায়।

Technical
Public GET /reviews সবসময় status: "PUBLISHED" দিয়ে filter করে। Moderation-এর পর কৃষকের reputation নতুন করে গণনা হয় (কারণ hidden review আর গোনা হবে না) এবং review_moderated audit entry লেখা হয়।

I. Database

প্রশ্ন ৪৬: আপনার ডাটাবেসে কতটি টেবিল? প্রধানগুলো বলুন।

সহজ উত্তর
১৫টি মডেল ও ১৩টি enum। প্রধান হলো User, FarmerProfile, Product, Cart/CartItem, Order/OrderItem, Review, TraceEvent, AuditLog।

Technical
১৮টি foreign key, ৯টি unique constraint, ১২টি index। সব primary key String @id @default(cuid())।

প্রশ্ন ৪৭: cuid কেন, auto-increment integer নয় কেন?

সহজ উত্তর
ক্রমিক সংখ্যা হলে URL দেখে যে কেউ বুঝে যেত মোট কতগুলো পণ্য আছে, আর ১, ২, ৩ করে সব দেখে ফেলতে পারত।

Technical
এছাড়া cuid একাধিক server থেকে একসাথে তৈরি করলেও সংঘর্ষ হয় না, এবং ক্লায়েন্টেই তৈরি করা যায় — ডাটাবেসের অপেক্ষা না করে।

প্রশ্ন ৪৮: Cascade আর Restrict কোথায় কোথায় ব্যবহার করেছেন?

সহজ উত্তর
যে ডেটা মালিক ছাড়া অর্থহীন সেখানে Cascade (Cart, CartItem, TraceEvent, OrderStatusEvent); আর যেখানে ইতিহাস রক্ষা করতে হবে সেখানে Restrict (Product ← OrderItem, OrderItem ← Review)।

Technical
Prisma-তে onDelete না লিখলে required relation-এর ডিফল্ট Restrict। Product ← OrderItem-এ ইচ্ছাকৃতভাবে কিছু লিখিনি, তাই Restrict কার্যকর — এবং এটিই soft delete-কে বাধ্যতামূলক করে।

প্রশ্ন ৪৯: AuditLog-এ foreign key নেই কেন?

সহজ উত্তর
কারণ যাকে নিয়ে লগ, সে মুছে গেলেও লগটি টিকে থাকা দরকার।

Technical
actorId ও targetId শুধু string snapshot। FK হলে cascade বা restrict-এর কারণে লগ হারিয়ে যেত বা লেখাই যেত না — অথচ audit log-এর পুরো উদ্দেশ্যই প্রমাণ ধরে রাখা।

প্রশ্ন ৫০: Migration কী? আপনি কয়টি চালিয়েছেন?

সহজ উত্তর
Migration হলো ডাটাবেসের গঠন পরিবর্তনের নথিভুক্ত ইতিহাস। আমার একটি migration আছে — 20260922135451_init।

Technical
এটি সম্পূর্ণ PostgreSQL SQL: ১৩টি CREATE TYPE, ১৫টি CREATE TABLE, ২১টি index ও ১৮টি FK। Production-এ prisma migrate deploy শুধু অপ্রয়োগকৃত migration চালায়, কিছু মোছে না — তাই এটি নিরাপদ। এটি Vercel-এর build কমান্ডেই যুক্ত।

প্রশ্ন ৫১: Seed কী? বারবার চালালে ডেটা দ্বিগুণ হবে?

সহজ উত্তর
Seed হলো ডেমো ডেটা ঢোকানোর স্ক্রিপ্ট। না, দ্বিগুণ হয় না — প্রতিটি রেকর্ড upsert বা অস্তিত্ব-যাচাই দিয়ে তৈরি।

Technical
একটি বিশেষ ক্ষেত্র ছিল: TraceEvent-এর কোনো স্বাভাবিক unique key নেই, তাই upsert করা যায় না। তাই প্রতিটি ধাপের আগে findFirst দিয়ে দেখে নেওয়া হয় — নাহলে দ্বিতীয়বার seed চালালে timeline-এ প্রতিটি ধাপ দুইবার দেখাত।

J. Security, Deployment ও Testing

প্রশ্ন ৫২: SQL injection ঠেকান কীভাবে?

সহজ উত্তর
Prisma সবসময় parameterized query তৈরি করে, তাই ব্যবহারকারীর লেখা কখনো SQL-এর অংশ হয় না।

Technical
আমার প্রজেক্টে কাঁচা SQL শুধু এক জায়গায় — app/ready/route.js-এ prisma.$queryRaw`SELECT 1`, যেখানে কোনো ব্যবহারকারীর ইনপুটই নেই। এছাড়া Zod প্রতিটি ইনপুটের ধরন আগেই যাচাই করে।

প্রশ্ন ৫৩: XSS নিয়ে কী ব্যবস্থা?

সহজ উত্তর
React নিজে থেকেই সব লেখা escape করে; আর আমি কোথাও dangerouslySetInnerHTML ব্যবহার করিনি।

Technical
এছাড়া ছবি আপলোডে SVG ইচ্ছাকৃতভাবে নিষিদ্ধ, কারণ SVG-তে JavaScript থাকতে পারে আর ফাইল আমাদেরই origin থেকে পরিবেশিত হয়। Download route-এ X-Content-Type-Options: nosniff দেওয়া আছে। তবে CSP header নেই — এটি একটি সীমাবদ্ধতা।

প্রশ্ন ৫৪: Rate limiting কীভাবে করেছেন?

সহজ উত্তর
একটি in-memory sliding-window limiter — যেমন login-এ এক মিনিটে সর্বোচ্চ ১০ বার। ছাড়ালে 429।

Technical
IP-ভিত্তিক key (x-forwarded-for থেকে), একটি Map-এ timestamp-এর তালিকা, আর প্রতিবার সময়-সীমার বাইরের entry বাদ দেওয়া। পাঁচটি endpoint-এ প্রয়োগ করা: login ১০, register ৬, farmer-verify ৮, image-upload ২০, product-archive ২০ — সবই প্রতি ৬০ সেকেন্ডে।

সীমাবদ্ধতা নিজে বলুন “এটি একক process-এর memory-তে থাকে, তাই একাধিক serverless instance-এ নির্ভরযোগ্য নয়। প্রকৃত production-এ Redis লাগত — কোডের কমেন্টেই আমি এটি লিখে রেখেছি।”

প্রশ্ন ৫৫: NID নম্বর কীভাবে সুরক্ষিত রাখেন?

Technical
maskIdentifier("BD-FARM-0001") → "********0001"। এটি toAdminFarmer() ও public farmer profile — দুটোতেই প্রয়োগ করা, এবং এর জন্য ৪টি unit test আছে যার একটি নিশ্চিত করে “কখনো মূল মান ফেরত দেয় না”।

প্রশ্ন ৫৬: কতগুলো টেস্ট লিখেছেন? কী পরীক্ষা করে?

Reputation গণনা (৪), image validation ও path traversal (৯), identifier masking (৪), earnings সারাংশ (৩), rate limiting (৩), review eligibility (৩)। সবগুলো node --test দিয়ে চলে, কোনো ডাটাবেস ছাড়াই — কারণ এই logic-গুলো ইচ্ছাকৃতভাবে pure function হিসেবে আলাদা রাখা।

প্রশ্ন ৫৭: প্রজেক্টটি কোথায় deploy করা?

সহজ উত্তর

প্রশ্ন ৫৮: Deploy করতে গিয়ে কোনো সমস্যায় পড়েছিলেন?

সহজ উত্তর
হ্যাঁ, তিনটি — এবং তিনটিরই মূল কারণ খুঁজে বের করে সমাধান করেছি।

বিস্তারিত
(১) Build-এ হোমপেজ ৬০ সেকেন্ডে টাইমআউট হচ্ছিল, কারণ সেটি static generation-এর সময় নিজের API-তে কল করছিল যখন server চালুই হয়নি — সমাধান: server-side-এ fallback + ৫ সেকেন্ডের timeout। (২) Production login-এ “Internal server error”, কারণ main branch-এ তখনো provider = "sqlite" — সমাধান: PostgreSQL branch merge করা। (৩) ছবি আপলোডে ENOENT mkdir /var/task/…, কারণ STORAGE_PROVIDER সেট করা ছিল না — সমাধান: object সেট করা।

টিপ এই প্রশ্নে বিস্তারিত উত্তর দিন — এটি প্রমাণ করে প্রজেক্ট সত্যিই deploy হয়েছে।

প্রশ্ন ৫৯: দুটি ডাটাবেস URL কেন?

সহজ উত্তর
DATABASE_URL pooled — অ্যাপ চলার জন্য; DIRECT_URL direct — শুধু migration-এর জন্য।

Technical
Serverless function ক্ষণস্থায়ী ও অসংখ্য; প্রত্যেকে নিজের সংযোগ খুললে PostgreSQL-এর সংযোগ-সীমা ফুরিয়ে যেত, তাই pooler। কিন্তু CREATE TABLE-এর মতো DDL-এর জন্য একটি স্থায়ী session লাগে, যা pooler দিতে পারে না — তাই migration সরাসরি সংযোগ ব্যবহার করে।

প্রশ্ন ৬০: আপনার প্রজেক্টের দুর্বলতা কী?

টিপ এই প্রশ্নে কখনো “কোনো দুর্বলতা নেই” বলবেন না। প্রস্তুত তালিকা থেকে ৩-৪টি বলুন, সাথে সমাধানের পথ।

প্রশ্ন ৬১: আবার শুরু করলে কী ভিন্নভাবে করতেন?

সহজ উত্তর

বিস্তারিত
SQLite দিয়ে শুরু করে পরে PostgreSQL-এ যেতে গিয়ে case-sensitivity-র মতো সূক্ষ্ম পার্থক্য ধরা পড়েছিল (admin search ভেঙে যেত)। আর ownership/IDOR-এর জন্য স্বয়ংক্রিয় টেস্ট থাকলে প্রতিটি পরিবর্তনের পর নিশ্চিত থাকা যেত।

প্রশ্ন ৬২: “AI-Enabled” বলছেন — AI কোথায়?

সৎভাবে বললে — এই সংস্করণে কোনো প্রশিক্ষিত AI মডেল নেই। nutrition, scanner, health prediction — সবই সূত্র বা heuristic।

টিপ এই প্রশ্নটি আসতে পারে এবং একটু কঠিন শোনায়। সরাসরি স্বীকার করে নিলে বোর্ড সন্তুষ্ট হন; লুকাতে গেলে বিপদ।

প্রশ্ন ৬৩: ১০,০০০ ব্যবহারকারী হলে কী হবে?
